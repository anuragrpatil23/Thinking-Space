# Key Blocks Reference

Annotated index of the blocks that carry non-obvious decisions. For general repo layout see [CODEBASE-GUIDE.md](../CODEBASE-GUIDE.md).

## Key Service Blocks (renderer)

- `frontend/src/services/lego_blocks/units/yamlNoteBlock.ts` — YAML frontmatter parse/stringify/validate/key generation
- `frontend/src/services/lego_blocks/integrations/dbBlock.ts` — Dexie.js IndexedDB cache layer
- `frontend/src/services/lego_blocks/units/aiPriceTableBlock.ts` + `frontend/src/data/aiModelPrices.json` — token counts to a dollar figure. Four rules, each violated in production: (1) **exact id beats pattern.** Lookup is three tiers — `overrides` (hand-written, wins over everything, carries a `reason`), `exact` (generated from the price feed, keyed by model id), `patterns` (hand-written regexes, first-match-wins, last resort). Every id in real transcripts now resolves *exactly*; patterns exist only for ids the feed has never published, such as a snapshot minted between refreshes. Regex-matching was the original failure mode, so it is no longer the only mechanism. (2) **no catch-all price.** `priceForModel` returns `null` for an unrecognised id and the UI renders "unpriced". The predecessor had a `FALLBACK_PRICE` and a catch-all `/opus/i` rule, so `claude-opus-5` — matching neither the current-Opus pattern nor anything else specific — silently landed on retired Opus 3 rates and reported **3x** the real cost for two model generations with no error (see `docs/contracts/DERIVATION.md:61`). Where a family's rate has genuinely changed, enumerate generations so the *next* model is unpriced rather than mispriced. (3) **A model family is not a price tier.** The GPT-5 line spans 15 tiers from $0.05 to $30 input; a single `/^gpt-5/` rule understated `gpt-5.5` by 3x while overstating `gpt-5.1-codex-mini` by 5x. (4) **The figure is a list-price equivalent, not a bill** — subscription plans meter against usage limits, so nobody is charged it, and every surface says so. Rates live in the JSON with `effective_from` + `source`. `scripts/refresh-ai-prices.mjs --build` runs as `prebuild` and auto-applies drift from LiteLLM's public feed, so a build never ships a stale rate; the app itself never fetches (locked decision #5), and an offline build warns and proceeds on the committed table. Two guards make auto-apply safe: the check resolves each model id **first-match-wins, exactly as the app does** — testing patterns independently invents conflicts and masks real ones (it hid a wrong `gpt-5.6` cache-write rate behind a bogus `o4-mini` conflict) — and a rule carrying `feed_disagreement` is never overwritten, which is how a considered position against upstream survives (`claude-sonnet-5` is held at $3/$15 because the feed still lists the introductory $2/$10). Expect the JSON to come back dirty after a build when upstream moves; commit it like a refreshed lockfile. `npm run prices:check` reports drift without writing.
- Token accounting in `nativeAiSessionParserBlock.ts` — **cost is a function of (model, bucket) pairs, so tokens are attributed per model** (`tokensByModel`), not per session. `model` on a session names its primary model for display and is *not* a costing input: a coordinator on Opus delegating to Haiku priced entirely at the session's model is wrong in whichever direction the last turn happened to fall. Buckets that spent nothing are dropped — Claude Code files its own notices under the model id `<synthetic>` with all-zero usage (132 across these transcripts, not one carrying a token), and keeping them would mark almost every session's total as incomplete over spend that never happened. Beyond that, both providers report **overlapping** buckets, and both traps inflate silently. Claude writes one API response across several assistant lines (a `thinking` line, a `tool_use` line) and **repeats the same `usage` object on each**; summing per line over-counted real transcripts by ~1.8x, so usage is keyed on `requestId` and counted once. Codex reports `input_tokens` *inclusive* of `cached_input_tokens`, and `reasoning_output_tokens` *inside* `output_tokens` (verified: `total_tokens == input + output` across 50,724 samples) — both are subtracted out, never added. Adding reasoning to output inflated Codex output, the expensive bucket, by 1.44x.
- `frontend/src/services/orchestrators/vaultSyncOrch.ts` — vault scan to IndexedDB sync
- `frontend/src/services/orchestrators/rssFeedOrch.ts` + `frontend/src/components/lego_blocks/integrations/RssTimelineBlock.tsx` — RSS article state is vault-backed only: `viewedAt` records meaningful automatic timeline exposure and `dismissedAt` records an explicit mark-read/skip; `read` is the compatibility projection of either. Do not revive the old localStorage read-ID fallback: it made state device-local and therefore apparently random across Mac/iOS. The timeline is a second view over the same feed model (iOS default; compact explorer retained), uses a 60%-visible / 900ms IntersectionObserver threshold instead of polling, and foreground refresh pulls changes written by another device.
- `frontend/src/components/lego_blocks/hooks/shared/useRssFeedsBlock.ts` — the single feed store every RSS surface reads. It lives at module scope (not a context) on purpose: the inline explorer panel and the mobile drawer panel can both be mounted at once on iOS, and each previously owned a private copy — two independent fetches of every feed and two divergent read ledgers. Module scope also means the store survives unmount, so reopening the reader paints cached articles instead of a spinner; a remount only triggers a background refetch once the cache is older than `STALE_AFTER_MS`. Every article mutation (viewed / read / saved / removed) goes through this store so the vault write and the optimistic update stay together. Nav (next/prev through the queue) is deliberately *not* shared — it is per-panel, and the inline panel owns it.
- RSS scroll position is anchored to an **article**, never a pixel offset (`RssTimelineBlock.tsx`, `pickRssTimelineAnchorBlock` in `rssFeedBlock.ts`). Three separate things used to destroy it, and all three must stay fixed: (1) iPhone detail mode slides the list off-screen at full width instead of collapsing it to `width: 0px` — a scroller squeezed to zero width has its `scrollTop` clamped to 0 by the engine (`ThinkingSpaceOrch.tsx`); (2) the timeline's rendered window is monotonic and must never shrink on data arrival, because retained-backlog pages stream in for seconds after open; (3) a background refresh must not clear `sessionReadIds`, or every just-read article drops out of the unread inbox and the list reshuffles. Card heights change as the backlog hydrates, which is why a raw `scrollTop` cannot work here.
- The merged RSS views (All Unread, timeline, reels) show one row per **article**, not per cached file (`collapseDuplicateRssEntriesBlock`, `rssArticleKeyBlock` in `rssFeedBlock.ts`). Item ids cannot identify an article: they are scoped to one feed and hashed from a guid that some publishers renew on every re-listing, so the same article is cached once per section feed and again on each re-list. The files are never deleted or merged — outside tools and annotation marks address them by per-feed id — the views collapse them and show an "also in …" note. The key is the link minus tracking parameters only; other query parameters stay, because some sources tell articles apart by a query id alone. Three rules keep this coherent: (1) the source filter is applied before collapsing, so browsing one feed still shows everything it carries; (2) read state is written to every copy at once in the store (`withDuplicatesBlock` in `useRssFeedsBlock.ts`), otherwise the article returns unread from the next copy; (3) feeds in a group marked `excludeFromAllUnread` are dropped from every merged view by `rssReaderFeedsBlock` and are outside read propagation — a tool reads those, and what the reader has seen says nothing about what the tool has.
- Feed merges are unions, never replacements (`unionRssFeedItemsBlock`). A live fetch only returns the publisher's current window, so replacing wholesale drops the hydrated backlog and makes the list visibly shrink and regrow. Collision rule differs by direction: a live result supersedes what is on screen, a retained-cache page must not clobber the live copy or an optimistic update. `patchRssFeedItemsBlock` / `dropRssFeedItemsBlock` preserve the identity of untouched feeds so one article changing does not re-render every other feed's rows.
- `frontend/src/services/orchestrators/vaultGraphOrch.ts` — vault graph data for the /vault-graph Tools subtab: **one unified graph over notes AND code** (decided 2026-07-17: no source toggle — a repo opened as a profile's vault maps with its docs clustered beside the code). Markdown gets wikilink edges (Dexie), code files get lexical import edges via `codeImportScanBlock` (units): per-language regex extraction (JS/TS family incl. `@/`→nearest-`src` alias heuristic, Python dotted/relative, Rust `mod`) resolved against the walked file set — no parser/LSP/package deps, renderer-side so the existing vault-guarded IPC covers it (no new main surface). Bare package imports never become edges; generated dirs (dist/build/out/coverage/target/vendor/…) are excluded for md too; code files >400KB stay nodes but aren't scanned; code scan capped at 6000 most-recent files. Git births run pathspec-free now (all files, not `*.md`). Plus git file births + AI-session heat; force-graph is dynamically imported in `VaultGraphCanvasBlock` only (startup contract). The graph can also be driven by the AI-activity card (lazy-mounted in a drawer): picking a day lights that day's touched notes, clicking a session zooms to the notes it touched. From the **home** AI-activity card (not the graph page), a session row also offers a graph **peek** without navigating away (added 2026-07-17): ⌘/Ctrl-click a row — or right-click → "Show in graph" — opens `SessionGraphSlideOverBlock` (lazy; keeps force-graph out of the eager home chunk), a right-side slideover mounting the same `VaultGraphCanvasBlock` lensed + zoomed to that session's files via `selectGraphNodesForChainsBlock`. Gated behind `AiActivityPanelBlock`/`AiActivityDayTableBlock` `enableGraphPeek` (off in graph-controller mode). Row hover warms `loadVaultGraph()` (shared 5-min snapshot + in-flight dedupe) so the first open is instant; a ⌘-click on a graph node opens that file. The graph snapshot is deliberately NOT persisted to the vault — it's derived data (locked decision #3: IndexedDB/in-memory is the rebuildable cache, the vault stays byte-identical markdown+YAML), and a vault-committed blob would churn on every edit and conflict across synced devices. Node attribution prefers **file-edit provenance** — `ParsedSession.touchedPaths`/`ActivityChain.touchedPaths` (absolute paths extracted from Claude `tool_use` Edit/Write/MultiEdit/NotebookEdit calls in `nativeAiSessionParserBlock`) mapped vault-relative by `selectGraphNodesForChainsBlock` in `vaultGraphBlock.ts`; falls back to the time-window heuristic (marked `approximate`) for chat sources / GC'd transcripts. Bump `CACHE_VERSION` in `aiActivityCacheBlock.ts` whenever the parsed-session shape changes (provenance landed on v16). Layout uses **folder gravity** (`makeCentroidForce` in `VaultGraphCanvasBlock`): every note is pulled toward its folder's centroid (strong) and its project's (gentle), so the human's own filing shapes neighborhoods instead of a wikilink hairball; wikilinks stay the weak cross-cluster threads.
- `frontend/src/services/lego_blocks/integrations/aiActivityCacheStoreBlock.ts` — the vault-shared AI activity cache on disk: `.thinking-space/ai-activity-cache/v<CACHE_VERSION>.<YYYY-MM>.json`, one file per month of session start. Writes go month by month and skip any month whose text (keys sorted, `updatedAt` masked) is unchanged, so normally only the current month is rewritten; emptied months and other-version files are deleted. Reads fingerprint each month and reuse unchanged parses; an unreadable month returns null (re-parse) rather than a partial cache. The pre-split single `ai-activity-cache.json` is read to migrate and deliberately left in place for older builds. Why: before the split (2026-10-16) the whole 4.1 MB file was rewritten on every transcript change, ~12×/h with agents running ≈ 50 MB/h of iCloud upload; on the real cache the current month is 247 KB of 4.06 MB across 44 files.
- `frontend/src/services/lego_blocks/integrations/aiActivitySnapshotStoreBlock.ts` — device-local IndexedDB persistence for AI activity (added 2026-07-19, fixes the multi-second cold-start load on iOS/iPad where WKWebView death wipes the in-memory snapshot). Two records, both keyed `(CACHE_VERSION, vaultRoot)`: the final deduped session snapshot (cold `loadAiActivity` seeds from it and returns instantly with `ts: 0` = stale, while the full load runs behind and fires `subscribeAiActivitySnapshotBlock` listeners — `useAiActivityBlock` adopts the fresh result silently), and a parsed mirror of the vault's `.thinking-space/ai-activity-cache.json` keyed by stat fingerprint (`mtime:size`), so an unchanged cache file skips the multi-MB bridge read + JSON.parse entirely (`readCache`/`writeCache` in `aiActivityCacheBlock`). `clearAiActivitySnapshot()` also drops the persisted snapshot (session-source settings changes must not resurrect excluded sessions). Derived data only — version or vaultRoot mismatch falls back to the full load; per-profile storage partitions scope it automatically.
- `frontend/src/services/orchestrators/vaultSearchOrch.ts` — THE vault search engine; every vault search surface should ask it instead of ranking its own list. Corpus comes from the IndexedDB index cache, never a disk walk: `files` (all markdown), `assets` (non-markdown names, recorded by sync's existing walk via `walkVaultForSyncBlock`), folders implied by both, and each note's title/tags/`searchText` (`getNodeSearchSummaries`). Built on first query, dropped when a sync fires `vaultIndexChangedBlock` (open searches re-run) or after 2 min idle (iOS memory). Ranking is the pure `vaultSearchRankBlock`: every token must match; name > title > tags > folder > content; letter-scatter only on names and only within 1.5× the token (unrestricted subsequence matching flooded 20k paths with junk); app-generated paths (`isAppGeneratedVaultPathBlock`) rank below the user's notes. `buildVaultSearchTreeBlock` lays hits out as a tree; `VaultExplorerBlock` filters through `useVaultSearchBlock`, drawing search branches from hits (no folder loading) and showing folders that matched by name whole. Measured on the real vault (~16k docs): 3–19 ms per query. ⌘K (`App.tsx`) is on it too: files come from `useVaultSearchBlock(…, { kind: 'file' })`, the palette's own commands are scored by the same `rankVaultSearchBlock` (as docs) so pages and files sort on one scale, and `UniversalSearchBlock preRanked` keeps that order instead of re-ranking with the old loose fuzzy matcher; empty query shows `listRecentVaultFilesOrch`. Other `UniversalSearchBlock` users (small in-memory lists) still rank locally. Full text: `fullTextIndexOrch` (writer + reader) over `fullTextIndexStoreBlock` (layout) with `fullTextTokenizeBlock` as the ONE definition of a word for both sides. Index lives in the vault at `.thinking-space/search-index/` so iCloud carries the Mac's work to the phone; git-ignored via the app-managed baseline; watcher-ignored, so writes can't loop. Base = per-first-letter shards (term → gap-encoded base36 doc ids) + a doc table, written as a new generation then swapped via the manifest; edits go to one small per-note delta file, never a shard; rebuild at >300 deltas or a week-old base. One writer: the install id in the manifest (a stranger waits out a 14-day grace). Deleted notes need no tombstones — results are filtered by the live corpus. Writer runs only after a sync signal (+ one pass 60s after launch); phones/web only read, so a phone edit is found by name/excerpt until the Mac indexes it. Lazy-loaded (own chunk) per the Startup contract. Measured on the real vault: 4,052 notes / 111 MB text → 7.5 MB index, ~40 shard files, 5.6 s build from disk. App-generated paths and notes > 1.5 MB are not indexed.
- Find in a note — ONE path for ⌘F and vault-search words (it replaced both the old `useInDocumentFindBlock` + `DocumentFindBarBlock` and a parallel search-hit pill, 2026-10-16). Model in `searchHighlightTermsBlock`: `NoteFindQuery` = `words` (the app-wide vault search words — explorer filter / ⌘K; full-text vocabulary, word-start match, so a note lights exactly what made it a hit) or `literal` (typed after ⌘F; a phrase finds that phrase); `findNoteMatchesBlock` is the only matcher. `MarkdownDocumentBlock` owns the state (typed text overrides the vault words for that note; a new vault search takes over again) and renders the one `NoteFindBarBlock` (pill: amber dot, editable words, “1 of 3”, ↑↓×) absolutely positioned over the pane — outside the scroller, so it never scrolls away. Painters: reading mode `useNoteFindInViewBlock` (CSS Custom Highlight API, shared Highlight objects since several notes stay mounted, MutationObserver so late renders are found, null until it has actually looked); edit mode `findMatchLayerBlock` (CM6 layer under the text, never mark spans) via `MarkdownRichEditorBlock findQuery/onFindMatches/onFindRequest` + handle `stepFind`; ⌘F in edit mode opens the note bar instead of CodeMirror's panel (editors without `findQuery` keep CM's). HTML pages use the same bar over webview find. Colours: `--ltm-find-match(-current)`, amber.
- `frontend/src/services/lego_blocks/integrations/vaultExternalChangeBlock.ts` — listener on the app-wide chokidar vault watcher for writes the app did not make (self-writes filtered). `VaultExplorerBlock` uses it to re-list the parent folder of an external add/unlink if that folder is loaded. Before this, the watcher only re-synced IndexedDB (`vaultLiveRefreshOrch` → `smartSync`) and never told the tree, which reads folders straight from disk — so agent-created files needed a manual refresh. `MarkdownDocumentBlock` uses it too: an external `change`/`add` of the open file swaps content in place (no `loading` flip, so scroll survives); a dirty editor gets the conflict banner instead, and an Excalidraw canvas in edit mode is left alone. Before this, an open page only re-read on the top-bar refresh event.
- `frontend/src/services/orchestrators/sessionTelemetryOrch.ts` — recent-session telemetry for the explorer: every AI session that wrote vault files in the last 12h (provenance-only, via `sessionTelemetryBlock.ts`), each split created-vs-edited by ctime-inside-session-span, plus an `all` union (created wins). Powers the touched-file dots + the count strip (`SessionTelemetryStripBlock`) in `VaultExplorerBlock` (wired via `useSessionTelemetryBlock`). Several agents usually write at once, so the strip defaults to all recent sessions and its chevron scopes dots/filter to one; the old "newest session replaces older" rule made the strip flip between concurrent agents. Deliberately ephemeral (12h age-out) — AI Activity is the durable record; dots are live telemetry, not an inbox. Live: each load overlays a fresh parse of only the native transcripts whose mtime moved past the AI Activity snapshot (never force that snapshot for this — it walks the vault and rewrites its iCloud cache file), and `subscribeSessionTelemetry` pushes a load ~1.5s after any external vault write (`vaultExternalChangeBlock`, riding the existing chokidar watcher) plus one 5s follow-up for a save that beat its transcript flush.
- `frontend/src/services/lego_blocks/units/navRailPrefsBlock.ts` — per-profile nav rail order/visibility ({order, hidden, homePosition} in localStorage, so profile partitions scope it automatically). Rail entry: press-and-hold a rail icon → iOS-style jiggle edit mode in App.tsx (drag to reorder, × to hide, Esc to exit); precise fallback in Settings → Navigation (`NavRailSettingsBlock`). Hiding is rail-only (pages stay routable + in ⌘K); ⌘1…n shortcuts and the mobile drawer consume the same filtered arrays so order stays in sync. Settings/avatar are fixed anchors, not manageable. **Home is repositionable** (added 2026-07-18): `homePosition` ('top' | 'bottom', **default 'bottom'** — the bottom corner above the profile switcher) is set by dragging the Home glyph in jiggle-edit mode between the top nav group and the bottom actions group (each is a drop zone that only reacts to the Home id `'/'`, so normal item-reorder drops pass through), or via the Home-position Top/Bottom toggle in `NavRailSettingsBlock`. Home stays non-hideable and is not interleaved among the reorderable items — it's a top-or-bottom anchor only. The dragged-id ref is cleared on `dragEnd` (not mid-drop) so a Home-dropped-on-an-item event still bubbles to the container drop zone. **Webull and Tools start hidden on a fresh profile** (2026-08-29): `seedNavRailDefaultsBlock()` runs from `main.tsx` before first render and writes the starting record once, because `hidden: []` and "never opened that panel" are otherwise the same stored state — flipping the default without it would have yanked both tabs from every existing user who never customized the rail. Two traps, both hit for real. (1) **`getStorageItem(STORAGE_KEYS.vaultRoot)` is not localStorage on Electron** — it routes through the preload bridge to a per-profile value, and a profile owns a vault root from the moment it is created (choosing the folder *is* how you create one), so it reports "prior use" on a profile seconds old. Prior-use detection reads `localStorage` directly for this reason. (2) **A cold boot writes storage before the seed runs**: `ltm-app-color-mode`, `ltm-app-shell-tabs`, `ltm-app-shell-active-tab-id`, `ltm-app-theme` (the last two per-window-suffixed) all land first, so they mean "the app started", not "someone used this", and are discounted — any *other* `ltm-*` key counts as use. Seeding is versioned (`SEED_VERSION_BLOCK`), not once-forever, so a record written by a superseded rule is reconsidered exactly once and only when it shows no human choice (empty order, empty hidden, default home position); anything else is merely re-stamped. Consequence accepted deliberately: a genuinely untouched existing install reads as new and gets both tabs hidden, one click from restored.
- `frontend/src/components/lego_blocks/integrations/AiActivityTrendSectionBlock.tsx` + `units/AiActivityTimeOfDayChartBlock.tsx` + `services/lego_blocks/units/aiActivityTimeOfDayBlock.ts` — **Trend answers "when", not "how much" (2026-10-16).** The stacked hours-per-day bars nearly duplicated Plan usage (same days, same colours, almost the same shape in a different unit). The default view is now one row per day, sessions placed on the 12a–12a clock: the day card's single-day timeline strip, stacked for the range. Sessions, not chains (a chain's span would paint idle gaps as work); midnight-crossing sessions split across rows; vault-markdown mirrors (start === end) draw as ticks; same-project blocks <10 min apart fuse, and overlaps draw longest-first in one row (lanes were tried and rejected: halved they read as hairlines, stacked they broke the one-row-per-day rhythm). Row ends carry the day's wall-clock total (overlaps counted once, `timeOfDayTotalsBlock`); the legend lists the top 4 (`LEGEND_TOP_PROJECTS`, Plan usage too) while hover cards list everything. Both charts share `CHART_GUTTER_PX` so their plots line up. Right-click switches to the old bars (`Hours per day`) and between colouring by project or by kind of work (`projectKindBlock`, disabled until a kind is set). Both are per-device localStorage prefs. The section is lazy-imported because the panel is reachable from the startup entry. Intended next layer: the user's thinking window as a band behind the rows, so building inside it is visible by eye.
- `frontend/src/components/lego_blocks/integrations/ProjectWorkRowBlock.tsx` + `hooks/shared/useProjectRangeSummaryBlock.ts` + `services/lego_blocks/units/rangeSummaryArcsBlock.ts` — **the "What you worked on" card, as glanceable project rows (2026-10-16).** The AI Activity card is the by-day view; this one is by project over the set. Each row is how much (bar = share of the set), when (one cell per day), and what (the range summary's theme titles); the paragraphs are the detail behind the chevron. The model's markdown is no longer rendered as-is: `parseRangeSummaryArcsBlock` reads the contract's strict `N. **theme** — meta. body` shape into arcs plus tail extras, and the row lays them out (the model's continuation indent used to leak through as a ragged first line). Anything off-format (the rules-based fallback, model drift) yields no arcs and the row shows session titles instead, which is also what it shows while the summary generates, so no row reads "Generating…". Known gap: arc meta (`2 sessions on Oct 16, ~1h 54m`) is still model-written; computing it needs the summary to return chain keys per arc. **Session titles come from the transcript**: Claude Code writes untimestamped `{"type":"ai-title"}` records (~90% of transcripts; `/rename` lands there too, last wins; no `custom-title` records exist in practice), and `nativeAiSessionParserBlock` now prefers it over the first prompt for `topic`. Rows carry `aiTitle` (`null` when absent), and the cache re-parses Claude rows lacking the field, the same no-CACHE_VERSION-bump trick as Codex `limitReadings`. Chain-digest titles still win over it where they exist (`useChainDigestBlock`). Not yet: Codex titles, and vault-markdown session mirrors (unknown whether the export keeps the record).
- `frontend/src/services/orchestrators/postItVaultSaveOrch.ts` + `services/lego_blocks/units/postItNoteBlock.ts` + `components/lego_blocks/integrations/CanvasSaveToVaultDialogBlock.tsx` — **"Save to vault" for canvas post-its (2026-10-16).** A post-it's text lives only in the canvas JSON (unsearchable, outside the hierarchy); saving writes it through `thoughts.create` (same capability and frontmatter as the composer) and then `convertPostItToNote` swaps the tile *in place* for a `note` tile (same id, rect, font size; the post-it colour carries over as the note tile's optional `color` corner mark). The swap happens only after the file is confirmed on disk, so a failed write leaves the post-it untouched. Names come from the first line (markdown markers stripped, cut at a word boundary, date fallback) and never overwrite (`findFreeNoteFilenameBlock`, now shared with the composer). The dialog is the folder tree plus the composer's own save-recents/usage counts, and saving records into them, so the two surfaces learn from each other; it deliberately skips the composer's `<project>/<kind>` composition, since a post-it already has its text and only needs a home. Removing the tile afterwards removes only the tile. Open follow-ups: an Inbox destination, then an end-of-day "save today's post-its" sweep built on the same orch. The auto "what I did with AI today" post-it (`useAiActivityPostItBlock`, opt-in, off by default) was deleted in the same change along with its setting and roaming pref; old tiles that carried `autoActivityState` load as plain post-its.
- `frontend/src/services/lego_blocks/units/noteComposerBlock.ts` + `frontend/src/components/orchestrators/useNoteComposerOrch.ts` — the New Note composer, split headless (2026-07-31). The block is pure (path/filename derivation, shortcut storage, project→destination derivation, usage counts, content meta, frontmatter preview, draft reconciliation); the orchestrator hook owns the state and the two write paths (`thoughts.create` / `todos.create` via the capability router, or `saveThoughtEdit` with mtime+hash conflict check when the destination note already exists). `pages/NewThought.tsx` is a view over it and holds only presentation state — doc/canvas surface, revealed panel, sheet/pill open, AI panel, and which popover is open (the project menu hung off the path itself, plus the settings panel). The boundary rule is "does it affect the saved note". The destination is a *composition*, not a path: `<project base> + <note-kind folder suffix>`, where the project half comes from the user's own project list (`.thinking-space/projects.json`, via `useProjectsBlock`) filtered to those with a vault-relative root, and the suffix is seeded by note kind and overridable afterwards (last action wins). Quick destinations — flat, hand-saved whole-path chips — were retired 2026-08-19 because they were users rebuilding that same composition by hand ("sfdl thoughts", "F9 thoughts"); the ones the picker cannot reproduce (a sub-area like `operations/sfw/airms/meetings`) migrate into the Explorer-picks list rather than being dropped. Two recents lists now exist and mean different things: `DESTINATION_RECENTS_KEY_BLOCK` is written on *save* (where the composer sent you), `BROWSED_DESTINATIONS_KEY_BLOCK` on *closing Browse* (where you went looking) — the panel shows the latter, since the project is picked from the path in the title bar and the panel's job is the sub-area case. Neither records per-click inside the tree: it commits as you click, so that filled the list with folders you passed through. This split was done specifically so the composer has an interface that isn't React: a native iOS composer would call these same actions over the Capacitor bridge. Destination selection is the intended first native surface (one bridge call per selection); the text surface is the hard one, since 60 Hz keystrokes can't round-trip and Swift would have to own the buffer locally.
- `frontend/src/components/lego_blocks/integrations/MarkdownRichEditorBlock.tsx` — **`drawSelection` is off on iPhone** (`drawSelection: !isIphoneRuntime`, 2026-08-01). It replaces the browser selection with CM6's own div layer and makes the native one transparent, but iOS hangs its grabbers, loupe, and second caret off the *real* selection — with it on you get a highlight you cannot adjust, no handles, and rectangles overhanging the text. The cost is the tuned `.cm-cursor` (2.5px accent caret + easeOutCubic glide, `iaTypographyProfileBlock`), which is that same div layer: gone on iPhone, and not recoverable — a native caret is not positionable by CSS. `.cm-content { caret-color }` takes the colour back and nothing else. Gate any caret styling on `isIphoneRuntime`, not `compactMobile`: where drawSelection is on it sets `caret-color: transparent`, and re-colouring there paints two carets. Toggling drawSelection per selection state was considered and rejected — the swap would land mid-long-press, exactly when iOS decides whether to attach grabbers, and it reintroduces a reconfigure on every selection change.

- `frontend/src/services/lego_blocks/units/pdfViewportBlock.ts` + `frontend/src/components/lego_blocks/integrations/PdfDocumentBlock.tsx` — PDF viewport geometry, reworked 2026-08-02 to close the "doesn't feel like Preview.app" gap. Three things carry the fluidity and all three are easy to regress. (1) **Page geometry is per-page.** The old code measured page 1 and applied it to every page, so any document mixing paper sizes or orientations got wrong placeholder heights → a lying scrollbar and content that jumps as real pages render. `usePdfPageMetricsBlock` (components/hooks/shared) measures every page's box in 24-page chunks on `requestIdleCallback` — page 1 first and alone so the fallback estimate lands immediately — calling `page.cleanup()` after each read and capping eager measurement at 600 pages (retained pdf.js page proxies are the iOS memory risk; see IOS-MEMORY). (2) **`<Page>` gets one document-wide `scale`, never a fixed `width`.** Passing `width` forces every page to the same width, which is exactly what breaks mixed-size documents; with `scale`, each page renders at its own natural size × the shared scale. (3) **Zoom anchors at the gesture focal point.** `computeZoomScrollAnchorBlock` returns the scroll offsets that keep the document point under the pinch centroid / cursor fixed across the re-raster (toolbar + keyboard zoom use the viewport centre); the CSS `transform-origin` follows the same point during the preview, and the correction is applied in a `useLayoutEffect` — after the relayout, before paint. - `frontend/src/services/lego_blocks/units/readingAttentionBlock.ts` + `canvasAttentionBlock.ts` + `readingForegroundBlock.ts` + `thinkingspaceReadingBlock.ts` + `useReadingAttentionBlock.ts` — **in-app reading time, rebuilt 2026-09-01 around measured attention instead of open-time.** The predecessor timed mount→unmount and looked at nothing else — not `active`, not visibility, not focus — so a document open behind another pane accrued full time; `MIN_DWELL_MS` (20min) and `MAX_SESSION_MS` (4h) were compensations, and they biased the log the worst possible way (only long sittings survived, and long sittings are the ones most contaminated by walking away). Leaving credits and freezes; returning resumes. `blur` is wired alongside `visibilitychange` because **in Electron a blurred-but-visible window never fires the latter**. The 5-minute ceiling bites in exactly one situation — window focused, nothing firing — which is genuinely ambiguous between deep reading and an empty chair; every other walk-away is caught by a real signal. `pointermove` is **canvas-only** and load-bearing there (a hovering Pencil generates moves and no touches, the same reason the wake lock covers Excalidraw in edit mode) and redundant on markdown, where it was also forcing a reflow mid-gesture — scroll sampling belongs in scroll handling, where layout is already clean. **One predicate, shared with the wake lock**, so a lease held while nothing is counted is impossible; instrumentation is opt-in via `countsAsReading` because `MarkdownDocumentBlock` also renders inside canvas tiles and memory-file lists that mount with `active`. **Foreground is exclusive, and it is a stack** — `MarkdownViewerOrch` is a global provider mounted in `main.tsx` that renders as a fixed overlay while the workspace document underneath keeps `active` true, so without an arbiter a wikilink click credited two documents from the same events; a stack rather than a slot because closing the overlay must hand attention back to what it covered. **Storage is one file per local day per install** (`ai-activity/raw-sessions/thinkingspace/reading/2026-09-01.a3f1c2.jsonl`): VaultFS has no atomic append, so a single growing log meant rewriting all history into an iCloud-synced *watched* directory on every close — the `home-snapshot.json` shape — and one shared file appended by a Mac and an iPad is a conflict copy waiting to happen (this vault already has `apple_screen_time/app_usage 2` to prove it). The filename doubles as an index; sealed days are parsed once and cached, and any file for *today* stays live including another install's. A horizon was the wrong fix — the panel has an `all` preset, so it would truncate history rather than bound work. **The record separates three things that were one**: `key` is the sitting's dedup identity (and its trailing field is the filed start, which is how an edit finds the day file after dragging a sitting across midnight — reading it from the right survives a `|` in a path), `uuid` is the document's identity so a rename stops splitting history (88/91 Excalidraw docs carry one, only ~24% of markdown, so it strengthens where available and readers fall back to path), and `filePath` is a hint. `startMs`/`endMs` stay wall-clock (*when*) with `activeMs` beside them (*how much*), because their ratio is how distracted a sitting was and cannot be recovered once collapsed. `method` distinguishes what the app observed from what a person asserted, and `mergeReadingRecordsBlock` never lets a measured emit stomp a declared one — the in-progress span is flushed on `pagehide`/hidden (closing a window does not reliably unmount React, and reading-then-quitting is a normal way to finish), so the real close re-emits the same key and the longer measurement wins. **`where` is a tagged union**: `scroll` carries max/end ratios, `canvas` carries stations. They are the same idea at different dimensions — a document has an extent so a position is one number; a canvas has none, so 25 minutes on one says almost nothing without *where*. A station is the viewport rect the attention rested in, opened when overlap with the current one drops below half (measured against the **smaller** rect, so zooming in and back out are symmetric). **The rect is the observation; which elements or frames it covers is recomputed on read** — cost does not scale with the canvas, zoom weighting stays a policy that can change later, and a frame drawn tomorrow explains attention from last month, which storing frame ids could never do. `elementIds` are sampled once per station close as a *drift hint*, not the answer: they agreed with the rect when written, so a disagreement on re-intersection means the scene moved and a reader can say so instead of confidently answering the wrong question — the same preference for an explicit orphan that `inkAnchorBlock` makes. Stations partition the total rather than duplicating it (`sum(stations.activeMs) === activeMs`, pinned by test including across a ceiling-clamped walk-away). Writes ride `getVaultWriteAiActivityAnyEnabled()` like manual sessions, and **that gate now treats an unreadable preference as permissive** — the prefs are only legible in Electron, so inheriting `false` meant reading was never logged on iPad, the device where most of it happens; same rule `powerStateBlock` applies to Low Power Mode. Known open question, deliberately not answered yet: the attention floor is per *sitting*, so hopping between five documents for 40s each records nothing, and an accidental long-press into edit mode splits a sitting in two. What counts as one sitting is the same question `buildChains` had to pin down, and it deserves the same characterization suite before it moves.

- `frontend/src/services/lego_blocks/units/aiLimitShareBlock.ts` + `services/orchestrators/aiLimitShareOrch.ts` — **how much of the plan's session and weekly limits one sitting used** (added 2026-10-07; shown in the day table's expanded row). Both providers report only an account-wide whole-number percentage and nothing about who spent it. The first design was a single dollars-per-percent rate applied to each session's cost, and it is wrong: on the author's log a dollar of one Opus generation moved the 5-hour meter ~40% further than a dollar of the next. So the block **measures instead of estimating** — between two readings the meter moved by N; if one session spent in that interval the N is its own, no rate involved (≈99% of intervals on real data). Rates exist only to divide an interval where several sessions spent, are fitted **per model from the single-spender intervals of the same data**, and are refitted once with outliers removed so an overnight jump cannot inflate the rate it is judged against. Rules that each fix a wrong number seen on real logs: (1) movement with no local spender is filed under `sid: null`, never handed to whoever reported it — a claude.ai chat or an unmirrored machine is invisible here, and absence is not evidence; (2) movement beyond 3x what local spend explains (+2 points of rounding) is capped and the rest unattributed; (3) a *new* window counts from zero only if it began after every window already tracked had reset — one account's windows never overlap, so an overlapping one is a second account or a window older than the log, with a past we never saw (Codex profiles rotate accounts; without this every switch re-attributed the other account's standing value); (4) a high-water mark per window, so a meter that dips a point and recovers is not counted twice; (5) spend between two of a session's samples more than 30 min apart is a step at the later one, not a ramp — a ramp hands slivers of everyone else's movement to a session that was idle. Summing a session's movements telescopes to last-minus-first, so rounding error is under a point per limit window touched, not per sample. **Nothing is stored**: shares are recomputed on read from stratum-1 capture, across every session at once, because who moved the meter cannot be answered for one session in isolation. A sitting with no reading of its own is *left out* of the result (renders nothing) rather than reported as 0%. **Sources differ by provider.** Claude Code never writes limits into a transcript, so Claude shares come from the status line's usage log (`aiUsageLogBlock` reads home over the `ai:usage-log:read` IPC plus every machine's vault mirror, deduped by `t|sid`) joined on session id — and therefore exist only from the day the status line was installed. Codex writes the percentages onto every `token_count` event, so the parser lifts them onto `ParsedSession.limitReadings` (thinned to readings where a meter moved, plus the last) and Codex shares need no setup and reach back through old transcripts; slots are assigned by `window_minutes`, not primary/secondary, because a plan with no short window reports the weekly one as primary. Capture side: `claude-statusline.sh` now samples **per session** (a `<sid>.stamp` beside the snapshot) and immediately whenever a percentage changes — the old five-minute clock was read off the log's last line, i.e. one clock per machine, which starved every concurrent session but the first to render; fine for a curve, fatal for attribution. Cache lever: **not** a `CACHE_VERSION` bump — a Codex row parsed before the field existed lacks `limitReadings` entirely (the parser always writes the array, empty included), and `aiActivityCacheBlock` treats that absence as not-fresh, so only Codex transcripts re-parse, only on the machine that can read them.

## Key PDF Reader Blocks

Rebuilt 2026-09-03. The viewer no longer uses react-pdf's `<Page>`; it drives
pdf.js directly so the bitmap can be decoupled from the layout box.

- `frontend/src/components/lego_blocks/units/PdfPageCanvasBlock.tsx` — one page.
  **The layout box and the bitmap are separate things.** The host div carries
  `naturalMetrics * displayedScale`; the canvas inside is always
  `width/height: 100%`. A zoom commit is therefore one inline style change and
  the existing bitmap is stretched by the compositor — instantly, with correct
  geometry — while a fresh raster lands asynchronously and swaps in. react-pdf
  drove the canvas backing store from a React prop, so every scale change tore
  down canvas + text layer + annotation layer for every windowed page and left a
  blank frame; that was the original "zoom snap". Renders into a **detached**
  canvas and swaps on success, so the old pixels hold until new ones exist.
  Draws in two passes (cheap, then sharp) with a rAF between so the cheap frame
  actually paints.
- `frontend/src/services/lego_blocks/units/pdfRasterBudgetBlock.ts` — how big a
  bitmap to make. Quantization ladder (~19% steps) so a pinch inside one rung
  reuses a bitmap; per-page pixel budget that **gives up device pixel ratio
  before raster scale** (dropping 2x to 1.4x is far less visible than softening
  the layout box). **The iOS ceiling is a time budget, not a memory budget** —
  pdf.js paints on the main thread, and 6 MP is roughly a second of blocked main
  thread on an iPad. Measured from a screen recording, not reasoned about.
- `pdfViewportBlock.ts` — two windows, not one. Pages raster and re-raster
  inside `buildPdfRenderedWindowBlock`; they keep the bitmap they already drew
  inside the wider `buildPdfRetainedWindowBlock`. A single window unmounted a
  page the moment it left it, so scrolling back one page showed an empty box
  where a rendered page had been a second earlier. Retained pages go soft after
  a zoom until they re-enter the render band — a much better failure than blank.
- `pdfPaperThemeBlock.ts` — paper tones as a **per-raster ImageData pass**.
  Never a CSS filter on a live canvas: that is exactly the Excalidraw failure in
  IOS-MEMORY.md, and its cost is per composite frame rather than per raster.
- `pdfLinkTargetBlock.ts` + `pdfPageLinksBlock.ts` + `PdfLinkPeekBlock.tsx` —
  citation/figure peek (2026-10). A link annotation gives a destination
  *point*, not a region; the peek derives the region from the link's own text.
  A reference crops to **one column**, recovered from the destination page's
  text runs, so the neighbouring column's entries never sit beside it. A
  figure/table shows a tall full-width band on **both** sides of the anchor,
  because LaTeX anchors floats inconsistently (top with `hypcap`, caption
  without it, and APA puts the caption above the image). The card rasters
  **only the crop** via `getViewport({ offsetX, offsetY })`, never a full page,
  and applies paper tone as the same ImageData pass. A click jumps and leaves
  a "Back to page N" chip; a tap on touch opens the peek with a Go button.
  **Figures and tables are located by their caption, not the link
  destination** (`getPdfCaptionIndexBlock`, built once per document). Caption
  typography gives the side: "Figure 3: text…" (LaTeX) sits under the image,
  a lone "Figure 4" label (APA) sits above it, tables are above in both. The
  same index turns plain-text "Fig. 3bc" mentions into links for PDFs built
  without hyperlinks (dotted underline). Link text is sliced out of the run
  by even glyph width with one character of slack, and classified from
  `before + text` because many templates link only the number of "Figure 2".
- Zoom feel (`PdfDocumentBlock`, 2026-10): **a magnifying glass on a spring**,
  tuned by hand against Preview. The pinch preview is a pure scale about the
  fingers with nothing clamped; at commit the real layout lands inside
  `flushSync` (no painted gap between preview and layout — that gap was the
  end-of-pinch "snap"), the pinch point is restored by **page + fraction**
  (`pendingPageAnchorRef`, exact; ratio math drifted because preview scales
  page gaps and padding), and whatever the layout cannot honour (centring,
  scroll ends) is played out as a spring from the painted position. A
  sideways pull on a narrow page, or past a wide page's edge, rubber-bands
  (56px reach) and lets go when **momentum is detected** (three shrinking
  deltas), not when the wheel goes quiet — macOS trails a swipe with a second
  of momentum. Movement is `transform` + `will-change` only while moving, so
  the GPU moves the column instead of repainting every page canvas. Scroll
  the viewer causes itself is hidden from title auto-hide
  (`ownScrollUntilRef`). After a zoom, a page that already has pixels skips
  the low-res raster pass (it read as a blurry "refresh").
- PDF header chrome (`PdfDocumentRuntimeBlock` in `MarkdownDocumentBlock.tsx`)
  is an **overlay** over the page viewport, not a row above it, so the title
  can slide away on scroll as a transform. Taking it out of flow instead
  resizes the viewport on every toggle and jumps the text. The toolbar docks
  into the header via portal (`toolbarHost`) and morphs into the floating
  pill once the title is away; with the header hidden it floats from the start.
- EPUB reader (`EpubDocumentBlock.tsx`, 2026-10): foliate-js vendored at a
  pinned commit in `src/vendor/foliate-js/` (provenance, local patch and update
  steps in its README; the PDF backend is not vendored). It shares the PDF
  reader's shell (`ReaderDocumentRuntimeBlock` in `MarkdownDocumentBlock.tsx`:
  header, peek, docked row / floating pill) and paper-tone choice; tones and
  type settings are CSS (`buildEpubReaderCssBlock`) because EPUB is reflowable
  text, not artwork. Position is a CFI per vault path
  (`thinkspc:epub-reading-positions`), which survives width, font and layout
  changes. Safety is SECURITY.md's EPUB rule. Lazy: `React.lazy` + dynamic
  import of foliate, so startup preloads are unchanged.
  Page turns are a 3D leaf (`epubPageFlipBlock.ts`): foliate pages by
  scrolling one wide section document, so there is no page to rotate — each
  turn serializes the section into script-free sandboxed iframes clipped to
  single pages, turns the live view instantly underneath, rotates the copied
  leaf over the spine, then drops the copies. The visible page area comes
  from the renderer's centred layout; the section iframe's own rect does not
  move as foliate scrolls. Chapter boundaries, RTL books, continuous scroll
  and coarse-pointer devices keep foliate's slide.
- `usePenInkCaptureBlock.ts` — Apple Pencil. **Neither `touch-action` nor
  `preventDefault` on the pointer event stops WebKit scrolling**; it decides a
  touch is a scroll inside its own touch pipeline before either is consulted, so
  a stroke dragged the page out from under the nib. `Touch.touchType === 'stylus'`
  on a non-passive `touchstart` is the only signal early enough. Selection
  suppression is written imperatively for the same reason — a React re-render is
  a frame late and the selection has already begun.
- `pdfAnnotationGeometryBlock.ts` + `pdfAnnotationSaveOrch.ts` — marks are
  written **into the PDF** as standard `/Highlight` and `/Ink` annotations via
  `saveDocument()` (incremental append, original bytes intact at the head of the
  file). Decision record TP-PA-T-386. Three traps, each of which cost a session:
  1. **The storage key must start with `pdfjs_internal_editor_`.** The worker's
     `getNewAnnotationsMap` skips every other key silently, so `saveDocument()`
     returns the document unchanged and the write succeeds — a no-op reporting
     success.
  2. **A highlight needs `outlines`, not just `quadPoints`.**
     `createNewAppearanceStream` iterates it; omitting it throws "outlines is
     not iterable". QuadPoints alone fills the dict entry and draws nothing.
     Wind the polygon TL -> TR -> BR -> BL; QuadPoints order is TL, TR, BL, BR,
     so using it directly draws a bow-tie.
  3. **Ink needs `paths.lines`, not just `paths.points`.** `points` feeds
     `/InkList`; the appearance is drawn from `lines`, a run of 6-tuples where a
     leading NaN means "line to" and anything else is a cubic bezier.
  The save refuses to report success unless the output is larger than the input,
  because every one of these failures otherwise looks like a successful save.
  **Verify payload changes with a node harness** (load the real PDF, apply the
  payload, save, read it back) rather than by reasoning — that is what finally
  found (2) and (3).

- `pdfReadingPositionBlock.ts` + `usePdfReadingPositionBlock.ts` +
  `pdfReadingPositionSyncOrch.ts` — the auto-bookmark (2026-10-03). A position
  is **page + fraction of that page's height**, never a scroll offset: pixels do
  not survive a different window width, zoom mode, or page boxes that are still
  being measured. Keyed by vault path (the same string on every device; a
  renamed file starts over), with the time the reader was last there.
  localStorage is the synchronous copy the viewer restores from. It roams
  through **one file per install**, `.thinking-space/reading-positions/<install>.json`:
  a device writes only its own and reads everyone's, newest `at` wins — the same
  no-shared-file rule as the reading day files, and deliberately not a group in
  `ui.json` (reading state that changes per page turn would race every real
  preference in a whole-file read-merge-write). Three things to keep:
  (1) **nothing is recorded until the reader touches the document** — before
  that every scroll is the restore itself, and stamping it with "now" would
  make a stale local position outrank the one another device has not finished
  syncing; (2) the restore is **re-applied on every layout change** (metrics
  landing, fit scale resolving, a newer roamed position arriving) until that
  first touch, because the first application lands against estimated page
  heights; (3) being back at the start is **stored, not deleted** — a missing
  entry loses to another device's older, deeper one. The page is located from
  the page boxes by binary search, not from `pageNumber`, which lags the scroll.
  The vault file is written 5s after scrolling stops and on background/close,
  only when changed. Only `countsAsReading` mounts take part.

**Method note, since it dominated the session.** Nearly every fix made by
reasoning about this viewer needed correcting later; every fix made after
measuring held first time. Two cheap tools did the work: `ffmpeg mpdecimate` over
a screen recording to count real stalls (filter to gaps with activity on *both*
sides, or the reader pausing to read counts as a freeze), and a node harness
against the real file for anything touching pdf.js payloads.
