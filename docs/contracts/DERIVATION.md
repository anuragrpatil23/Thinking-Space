# Derivation Contract (Enforced, learned 2026-07-29)

The AI-activity / Thinking-Organizer stack is strata: raw sessions → chains → chain digests → ranges/atoms → undertakings. Each layer is a pure function of the one below it, plus a tiny set of durable human inputs (an undertaking's `head`, `tags`, `section`, `grew_out_of`). Everything else is derived and must be reconstructible from stratum 1. Four bugs in one cycle all came from breaking that in a different place, so the rule is written down.

- **Derived data must never be identity or an address.** (Learned 2026-08-01. This is the root rule; the two below it are what it looks like when broken.) A chain digest was stored at `chains/<projectId>/<date>/<chainKey>.md` — and `date` and `chainKey` are both *outputs of the grouping algorithm*. So every change to how sessions group renamed the file, orphaning the record it was supposed to update: the reader looked where the new grouping said the record should be, found nothing, and paid for a fresh provider call to regenerate a title that was already on disk under the old name. The same mistake sat in `UndertakingRecord.chains`/`fedBy`, which pointed at chains by the name they had at import time. The fix has three parts, and they generalise: **identity is minted once and frozen** (`chainId`, never recomputed, the file's only address — now flat at `chains/<projectId>/<chainId>.md`); **membership is how you find it again** when the id is unknown (`sessions[]` on the digest, resolved by overlap in `resolveChainDigestsBlock` — a chain *is* its sessions, so a rename cannot lose it); and **the records are their own index**, since a side table mapping session → digest is one more derived copy that can go stale. Corollary: keep the derived name out of the freshness hash. `computeChainInputHashBlock` deliberately excludes `chain.key`, because renaming a record must never cost a model call.

- **A chain groups by time; an undertaking is a topic. Don't let one answer for the other.** (Learned 2026-08-01.) A window ending 18:41:03 and a session starting 18:41:23 on the same project are one chain by the idle rule, and correctly so — but they can be about two unrelated things, and an undertaking points at *one* sitting. Flattening the chain's writes into a single `filesWritten` threw away which session made which, so the Broadcom drawer listed four notes belonging to the topic that followed it. The fix keeps the attribution the parser already has: `filesBySession` on the digest (`ParsedSession.touchedPaths`, never flattened away), `pointerSessionIdBlock` to read the session a record's chain pointer names, and narrowing that is deliberately timid — it applies only when attribution exists for more than one session, a pointer resolves to a session that chain holds, and the result is a proper non-empty subset. Everything else shows the full union exactly as before, because a page silently vanishing from an undertaking is the worse failure. `filesWritten` stays as the flattened union: older readers depend on it and it is recomputable from `filesBySession`.

- **A freshness hash must cover every input the output depends on.** `computeChainInputHashBlock` (`aiActivityChainDigestOrch.ts`) hashed only the title/summary inputs, but the digest also stored file pointers. So 460 digests written before pointer extraction existed matched their own hash forever and the fast path kept returning them with empty pointers — frozen memoirs that viewing could never heal. When you add a persisted field, either add it to the hash or derive it outside the hash (next rule). Never persist a field the freshness check ignores.

- **Separate model-derived fields from mechanically-derived fields.** Title and summary cost a model call and belong behind the model-freshness hash. Pointers and `activeDurationMs` come from the transcript's structured tool calls and per-message timestamps — free, deterministic — and must not be gated behind the model hash. They are projected from the chain on read and patched on drift (`projectChainFieldsBlock`), no model call. Guard the patch so a device that cannot see the transcript (iPhone/web: no IPC to `~/.claude`, so `touchedPaths`/`activeDurationMs` are absent) leaves stored values alone instead of overwriting good data with empty — absence means "nothing better to offer", not "zero".

- **Don't guard a copy — stop trusting it.** (Learned 2026-08-01, the same defect a third time.) A derived record can go stale because its *input* changed or because the *deriving code* changed, and `inputHash` only ever covered the first. So each pipeline move — `buildChains` learning to split concurrent sessions, then `filesWritten`, then `activeDurationMs` — left every existing record matching its own hash forever, and each was answered with another hand-written field comparison. Result: 462 of 469 stored digests at schema v1, 5 carrying pointers, while 397 sessions had correct provenance in the cache the whole time; the undertaking index rendered as a memoir. The first fix attempt was a `DERIVATION_VERSION` lever to mark those copies stale — a fourth patch on the same wound. The real fault is that mechanically-derived fields were *copied into* the digest and then read back as if authoritative. **A reader that can recompute a value must recompute it, and ignore what is stored.** `listProjectChainsOrch` joins every stored digest to the live chain and projects the mechanical fields over it (`projectChainFieldsBlock`); the on-disk copy is refreshed as a fire-and-forget side effect, purely as transport for devices that cannot derive chains locally (iPhone/web have no IPC to `~/.claude`). A stale copy is then unobservable on any device that could have noticed, so there is nothing left for a version to guard, nothing to migrate, and no rebuild command to run. This is the same rule the undertaking tail already followed — recomputed on every read, never stored.

- **Persist a derived value only to move it somewhere it cannot be derived.** That is the whole legitimate reason a copy may exist, and it dictates how it is read: as a fallback, last. It also dictates the no-stomp guard — a device with nothing better to offer (`touchedPaths` absent, not empty) must leave the transport value alone rather than overwrite good data with zero. If you cannot name the device that needs the copy, don't write it.

- **Every read path must reach the heal, or the heal does not exist.** Reconciliation lived inside `ensureChainDigestOrch`, whose callers are the chain view and the atom generator. The organizer reads chains through `listChainsBlock`, which parses digest files straight off disk — so for the entire undertaking surface the self-healing code was unreachable. When you add a repair, enumerate the read paths and confirm each one goes through it; a repair wired to one of three callers is a repair that mostly does not run. Better still, follow the rule above and make the repair unnecessary: `listProjectChainsOrch` is now the single chain read for the organizer, and it derives rather than repairs.

- **Canonical derivation belongs in services, never in a component memo.** Chains were built only in a `useMemo` inside `useAiActivityBlock`, over the *filtered* session list (range preset + source filter). Chain identity is `project::firstSessionPath`, so the visible window could change a chain's key and therefore the filename any digest was written under. Derivation that varies with UI state cannot be reconciled against anything, because there is no single answer to "what are this project's chains". `deriveCanonicalChainsOrch` is that answer — every session, unfiltered. A hook may keep a filtered *view*; persistence and reconciliation read from the canonical source.

- **`buildChains` is the seam; change it only against its characterization suite.** What counts as one logical session decides chain keys, digest addresses, undertaking membership and every duration in the UI — and it had no tests at all, which is how it was quietly changed three times, each time breaking something downstream that nobody connected back to it. `tests/aiActivityBuildChains.test.ts` pins the rules that are *correct*: group by project and time and never by topic, split on a `/clear` or an overlap, measure the gap from the chain's latest end (start-to-start for zero-length vault rows), sum aggregates, keep absence distinguishable from zero. Add the desired behaviour as a failing test first, then change the algorithm, then prove the rest still passes. Related: the idle threshold is one exported constant (`IDLE_GAP_MS`), used both to window a JSONL file and to chain sessions — two copies of "what counts as idle" can disagree, and a file that splits into windows which immediately re-merge into one chain is invisible in the UI.

- **A derived layer must fail loudly, not degrade in silence.** The range labeler had a flat 500-token budget for output that grows one line per chain, so past ~34 chains the assignment list truncated silently, unassigned chains defaulted to `Misc`, and the whole range fell back to stitched titles with no error. Silent degradation hid a hard ceiling for weeks. If a derived step can't do its job, it must say so (log/throw/tag the record with what actually ran, as the range `provider` field does) — never return a plausible-looking lesser result unmarked.

- **Verify the input is present, not just that the output code exists, before declaring a derived value available.** The dry run concluded "chains carry no file references" by reading stored chains; the pipeline had been extracting them all along and the digest dropped them on write. Reasoning backward from "the extraction code exists" to "the value is present" skipped the write path. Walk the whole edge, both ends.

- **Hooks capture; the app derives.** Capturing must happen at session end, outside the app, because the transcript can be pruned (rendering the raw-session markdown is genuine capture). Deriving is idempotent and runs any time the app next looks, so it belongs in the app, in TypeScript, next to the parser that already does it. A 278-line Python re-extractor (`scripts/session-pointers.py`, deleted 2026-07-29) violated this — it re-did derivation the app already performs and wrote frontmatter nothing consumed. Corollary: never write derived data back into stratum-1 raw files, the same mistake as caching an undertaking's derived tail into its record (which is why the tail is recomputed on every read and never stored — see [KEY-BLOCKS.md](../reference/KEY-BLOCKS.md)).

- **The AI write boundary is hard.** AI may write chain titles/summaries, range bodies, `proposedTags`, and pending assignments. A human writes `head`, `tags`, `section`, `grew_out_of`, and every accept/reject. AI never writes `tags` — `proposedTags` exists precisely so a machine guess cannot become the real vocabulary by sitting in the field the app reads. Same shape as the renderer/main trust boundary in [SECURITY.md](SECURITY.md): a line, not a preference.
