# Derivation Contract (Enforced, learned 2026-07-29)

The AI-activity / Thinking-Organizer stack is strata: raw sessions → **session digests** → chain views → ranges → undertakings. Each layer is a pure function of the one below it, plus a tiny set of durable human inputs (a session's `undertaking`; an undertaking's `head`, `tags`, `section`, `grew_out_of`). Everything else is derived and must be reconstructible from stratum 1. Four bugs in one cycle all came from breaking that in a different place, so the rule is written down — and every rule added since arrived the same way.

**Only the bottom layer reads raw material.** One model call per sitting, over that sitting's transcript; everything above composes those outputs. A chain is not stored at all (see the first rule), and the day tier that once sat between chains and ranges was deleted 2026-08-16 having never had a caller.

- **Derived data must never be identity or an address.** (Learned 2026-08-01; resolved properly 2026-08-14. This is the root rule — most of the others are what it looks like when broken.) A chain digest was stored at `chains/<projectId>/<date>/<chainKey>.md`, and `date` and `chainKey` are both *outputs of the grouping algorithm*. Every change to how sessions grouped renamed the file and orphaned the record it was meant to update: the reader looked where the new grouping said it should be, found nothing, and paid a provider call to regenerate a title already on disk under the old name. The same mistake sat in `UndertakingRecord.chains`/`fedBy`, which pointed at chains by the name they had at import time.

  The first fix kept the address and defended it: a `chainId` minted once and frozen, a persisted `sessions[]` acting as its own index, two-pass membership-overlap resolution to find a record whose key had moved, a reconcile pass, and a legacy nested-path fallback. It worked, and it was several hundred lines of machinery whose entire job was to survive an address that moves.

  **The real fix is to move the record to a layer whose identity is not derived.** A session id is stratum-1 — the Claude Code UUID, read off the transcript — so a digest filed under it cannot be orphaned by any change to grouping. Every one of those defenses was then deleted rather than simplified: there is no `chainId`, no `resolveChainDigestsBlock`, no reconcile orchestrator, no `filesBySession` (which existed only to undo the flattening a chain forced). A chain became an *answer* composed on read, memoized by its own content, filed nowhere.

  Corollary that generalises past this stack: when you find yourself hardening an address, check whether the record is at the wrong altitude. Defending a derived address is a cost you pay forever; moving the record is a cost you pay once.

- **An address is whatever is already written on disk — never narrow it to what you would have chosen.** (Learned 2026-08-01, while consolidating projects.) A project has two frozen fields, `uuid` (identity, minted once) and `key` (its on-disk address — `ai-activity/chains/<key>/`, the `project:` in every organizer record). The tempting validator restricts `key` to a directory-safe charset. That is wrong: 17 chain digests in this vault carry `projectId: Understanding Myself`, with a space, because the key is the canonical *project string* and `sanitizeSegment` derives the directory (`Understanding_Myself`) from it separately, downstream. The narrow rule would have set that project's key to `''` and dropped it from the registry silently. Validate an address only against what would make it *ambiguous* (path separators, dot-entries, control characters), and when a stored one fails, empty it rather than rewriting it — a sanitized key is a *different* address that nothing is filed under. Corollary, same shape as the pointer rule below: attribution has a precedence ladder (explicit rule → cwd inside a registered root → alias on the detected name → raw basename) and path evidence must outrank name evidence, or a folder named `backend` inside one project gets claimed by another. That ladder is pinned in `tests/aiActivityCanonicalProjectBlock.test.ts`, because every rung fails silently.

- **A name is a label; the key is the address.** (Learned 2026-08-01, wiring the project registry.) Renaming a project in Settings changed nothing in the AI-activity views, because everything downstream — grouping maps, React keys, palette slots, `ai-activity/chains/<key>/` — is keyed by the canonical project string, and nothing read `name`. The wrong fix is to rewrite the canonical string to the new name: that moves the address (see the rule above), splits the project's history in two, and orphans every organizer record filed under the old one. The right split is `projectLabelBlock(key)` — a warm-once `key → name` cache alongside the alias and color caches, read *only* where text is rendered. If a change to a name can alter a `key=`, a grouping key, a palette slot, or a path, it is in the wrong place.

- **Assign at the altitude the transcript actually distinguishes.** (Learned 2026-08-01; closed 2026-08-14.) A chain groups by *time*, so it can hold two unrelated topics: on 2026-07-09 an Important-Personalities window ran 18:35–18:41, a `/study-company` Broadcom session started 18:41:23, and 20 seconds on one project is one chain by the idle rule. The Broadcom undertaking then listed four personality notes as its pages. An undertaking is a *topic*; binding it to a time grouping cannot be made correct, only made luckier — the tempting patch (resolve the chain pointer to its head session and show only that session's files) resolves to the *personalities* window, and would have shown exactly the wrong page on any chain whose head session wrote.

  The fix was not a better pointer but a finer unit: assignment now binds to the **session**, which is the smallest thing the transcript distinguishes, so a mixed chain can no longer misattribute — the ledger keys on session id, and a chain's `undertaking` is the union of its members'. The queue still *groups* rows by sitting for triage, because grouping is presentation; disposition is data. Corollary: when a mapping keeps producing wrong answers, check whether its domain is coarser than its range.

- **A freshness check over inputs cannot catch a change in the deriving code, and each layer has its own lever.** (Learned repeatedly; three times on 2026-08-14 alone, which is why it is stated this way now.) The original form of this rule was narrower — `computeChainInputHashBlock` hashed the title/summary inputs but not the file pointers the digest also stored, so 460 records matched their own hash forever and the fast path kept returning them empty. True, and not the general case.

  The general case is that a derived record goes stale either because its *input* changed or because the *code that derived it* changed, and a hash over inputs only ever sees the first. This stack has three levers and each covers exactly one layer:

  | lever | in | bump when |
  |---|---|---|
  | `CACHE_VERSION` | `aiActivityCacheBlock` | the parser's output shape changes |
  | `promptVersion` | a contract | the prompt, or what is fed to it, changes |
  | `inputHash` | a record | a persisted field is added |

  All three were missed in one afternoon. Clipping a transcript to its window changed what the model saw without touching message count, window bounds or mtime — `promptVersion` was the only thing that could say so. Anchoring window ids to their first event changed what the *parser emitted*, and shipped completely inert because transcripts hadn't changed and nothing re-parsed; the user found it, not the tests. Then the same parser change needed the same bump again a commit later. Every entry in `CACHE_VERSION`'s own history (v12, v13, v15, v16, v18, v19, v20) is this lesson learned once more. **If you changed code that produces a stored value, name the lever before you commit.**

- **Separate model-derived fields from mechanically-derived fields.** Title and summary cost a model call and belong behind the model-freshness hash. Pointers and `activeDurationMs` come from the transcript's structured tool calls and per-message timestamps — free, deterministic — and must not be gated behind the model hash. They are projected from the session on read and patched on drift (`projectSessionFieldsBlock`), no model call. Guard the patch so a device that cannot see the transcript (iPhone/web: no IPC to `~/.claude`, so `touchedPaths`/`activeDurationMs` are absent) leaves stored values alone instead of overwriting good data with empty — absence means "nothing better to offer", not "zero".

- **Don't guard a copy — stop trusting it.** (Learned 2026-08-01, the same defect a third time.) A derived record can go stale because its *input* changed or because the *deriving code* changed, and `inputHash` only ever covered the first. So each pipeline move — `buildChains` learning to split concurrent sessions, then `filesWritten`, then `activeDurationMs` — left every existing record matching its own hash forever, and each was answered with another hand-written field comparison. Result: 462 of 469 stored digests at schema v1, 5 carrying pointers, while 397 sessions had correct provenance in the cache the whole time; the undertaking index rendered as a memoir. The first fix attempt was a `DERIVATION_VERSION` lever to mark those copies stale — a fourth patch on the same wound. The real fault is that mechanically-derived fields were *copied into* the digest and then read back as if authoritative. **A reader that can recompute a value must recompute it, and ignore what is stored.** A reader holding a session projects the mechanical fields over the stored digest (`projectSessionFieldsBlock`) and refreshes the on-disk copy as a fire-and-forget side effect, purely as transport for devices that cannot see `~/.claude`. A stale copy is then unobservable on any device that could have noticed, so there is nothing left for a version to guard, nothing to migrate, and no rebuild command to run. The chain layer went one better and kept no copy at all. This is the same rule the undertaking tail already followed — recomputed on every read, never stored.

- **Persist a derived value only to move it somewhere it cannot be derived.** That is the whole legitimate reason a copy may exist, and it dictates how it is read: as a fallback, last. It also dictates the no-stomp guard — a device with nothing better to offer (`touchedPaths` absent, not empty) must leave the transport value alone rather than overwrite good data with zero. If you cannot name the device that needs the copy, don't write it.

- **Every read path must reach the repair — or better, delete the repair.** Reconciliation once lived inside `ensureChainDigestOrch`, whose callers were the chain view and the (now deleted) atom generator. The organizer read chains through `listChainsBlock`, which parsed digest files straight off disk, so for the entire undertaking surface the self-healing code was unreachable: a repair wired to one of three callers is a repair that mostly does not run. When you add one, enumerate the read paths and confirm each goes through it.

  The better ending is the one this layer eventually reached: there is no repair now, because there is nothing stored that could drift. Chain-level content is composed on read from session digests, and the grouping is re-derived from those same records. A repair you cannot forget to call is one that does not exist.

- **A position is not an identity, however stable it looks.** (Learned twice on 2026-08-14, at two altitudes.) `chainId` was seeded from "which session sorts first"; a window id was `::w2`, meaning "the third window the splitter produced". Both are *ranks*, and a rank is stable right up until the thing doing the ranking changes. Window ordinals in particular look safe under the common case — a transcript is time-ordered, so an append can only open a new gap at the end and existing indices hold — and shift exactly when the windowing does: `IDLE_GAP_HOURS` moving, or Claude Code pruning events out of the middle.

  What makes this worth its own rule is that the *damage is uneven*, and the harmless half hides the other. Model-derived fields survive a renumber, because the freshness hash covers the window bounds and they simply regenerate. The human `undertaking` field does not: it is not recomputable, and it slides silently onto a different span of work. So the layer looks fine while the only irreplaceable thing in it is corrupted. A window is now named for the **first event it contains** (`<session-uuid>::<event-uuid>` — Claude Code writes a `uuid` on every event; Codex has none, so its windows fall back to the first event's timestamp, still content rather than order). Ask of any id: if the algorithm that produced this re-ran differently, would this name still mean the same thing?

- **Absence is not evidence.** Two shapes, both shipped. The mechanical one: a device with no IPC to `~/.claude` parses sessions with no `touchedPaths` and no timing, and must leave stored values alone rather than overwrite good data with empty — absence means "nothing better to offer", not "zero". The interpretive one is worse because it is a *narrative*: the day table rendered "No token data — this chain came from the vault markdown source only" whenever tokens were missing, so a native Claude transcript with an unattributed window was described to the user as a vault export. No tokens meant no tokens. It did not mean anything about where the row came from. When you find yourself explaining *why* a value is missing, check that you measured the reason rather than inferred it from the gap.

- **A record has two stores; a rename costs whatever the serialized one charges.** (Learned 2026-08-16, having made the same mistake earlier the same day.) `ProjectRangeSummary.body` was renamed to `.summary` on the reasoning that the prose is the markdown body on disk, read positionally — so the rename was free. That was true of the vault mirror and false of the intelligence-cache sidecar, which serializes field *names*. Every cached record still said `body`, `.summary` parsed as undefined, and the home route crashed reading `.length` off it.

  The identical shape had already appeared hours earlier: deleting session digest files from the vault changed nothing, because `getProjectSessionDigestBlock` reads the cache first and the cache answered. **Every record in this stack lives in both a vault mirror and a cache sidecar, and they do not fail alike** — the mirror keys prose positionally and frontmatter by name; the sidecar keys everything by name. Before claiming a schema change is free, open one record from each.

- **Green tests are not evidence that a pipeline ran.** Of the bugs found after the 2026-08-14 restratification, four surfaced because a human looked at real output and said "that is probably not true", and none came from the suite. Tests confirmed each fix in isolation while missing that the stage *in front of* the fix was serving cached work — a correct clip fed by a stale parse, a correct id emitted by code nothing re-ran. The suite cannot see a lever that was not bumped, an inert deploy, or a layer with no callers. For a change to a derived layer, "typechecks and 1000 tests pass" is the beginning of verification: drive the surface and read the output, or say plainly that you have not.

- **Canonical derivation belongs in services, never in a component memo.** Chains were built only in a `useMemo` inside `useAiActivityBlock`, over the *filtered* session list (range preset + source filter). Chain identity is `project::firstSessionPath`, so the visible window could change a chain's key and therefore the filename any digest was written under. Derivation that varies with UI state cannot be reconciled against anything, because there is no single answer to "what are this project's chains". `deriveCanonicalChainsOrch` is that answer — every session, unfiltered. A hook may keep a filtered *view*; persistence and reconciliation read from the canonical source.

- **`buildChains` is the seam; change it only against its characterization suite.** What counts as one logical session decides chain keys, digest addresses, undertaking membership and every duration in the UI — and it had no tests at all, which is how it was quietly changed three times, each time breaking something downstream that nobody connected back to it. `tests/aiActivityBuildChains.test.ts` pins the rules that are *correct*: group by project and time and never by topic, split on a `/clear` or an overlap, measure the gap from the chain's latest end (start-to-start for zero-length vault rows), sum aggregates, keep absence distinguishable from zero. Add the desired behaviour as a failing test first, then change the algorithm, then prove the rest still passes. Related: the idle threshold is one exported constant (`IDLE_GAP_MS`), used both to window a JSONL file and to chain sessions — two copies of "what counts as idle" can disagree, and a file that splits into windows which immediately re-merge into one chain is invisible in the UI. The grouping itself is likewise one generic (`groupChainableBlock` over `{project, startedIso, endedIso, hadClear, chainSortKey}`) with two adapters, live transcripts and stored digests, pinned equal by `tests/aiActivitySessionDigestGrouping.test.ts`. That equality is load-bearing: it is what lets a device with no access to `~/.claude` re-derive the same sittings from records alone, and therefore what makes a chain-shaped transport file — whose address would have to be derived from the grouping — unnecessary.

- **A derived layer must fail loudly, not degrade in silence.** The range labeler had a flat 500-token budget for output that grows one line per chain, so past ~34 chains the assignment list truncated silently, unassigned chains defaulted to `Misc`, and the whole range fell back to stitched titles with no error. Silent degradation hid a hard ceiling for weeks. If a derived step can't do its job, it must say so (log/throw/tag the record with what actually ran, as the range `provider` field does) — never return a plausible-looking lesser result unmarked.

- **Verify the input is present, not just that the output code exists, before declaring a derived value available.** The dry run concluded "chains carry no file references" by reading stored chains; the pipeline had been extracting them all along and the digest dropped them on write. Reasoning backward from "the extraction code exists" to "the value is present" skipped the write path. Walk the whole edge, both ends.

- **Hooks capture; the app derives.** Capturing must happen at session end, outside the app, because the transcript can be pruned (rendering the raw-session markdown is genuine capture). Deriving is idempotent and runs any time the app next looks, so it belongs in the app, in TypeScript, next to the parser that already does it. A 278-line Python re-extractor (`scripts/session-pointers.py`, deleted 2026-07-29) violated this — it re-did derivation the app already performs and wrote frontmatter nothing consumed. Corollary: never write derived data back into stratum-1 raw files, the same mistake as caching an undertaking's derived tail into its record (which is why the tail is recomputed on every read and never stored — see [KEY-BLOCKS.md](../reference/KEY-BLOCKS.md)).

- **The AI write boundary is hard.** AI may write session titles/summaries, composed chain and range bodies, `proposedTags`, and pending assignments. A human writes a session's `undertaking`, plus `head`, `tags`, `section`, `grew_out_of`, and every accept/reject. Corollary learned when assignment moved to the session: a human field must not be written through the path that regenerates derived ones — `patchSessionUndertakingBlock` bypasses the vault-mirror preference deliberately, because that setting governs copies that can be rebuilt and an assignment cannot. AI never writes `tags` — `proposedTags` exists precisely so a machine guess cannot become the real vocabulary by sitting in the field the app reads. Same shape as the renderer/main trust boundary in [SECURITY.md](SECURITY.md): a line, not a preference.
