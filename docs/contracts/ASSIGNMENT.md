# Assignment Contract (Enforced, written 2026-08-02)

Sessions say *what happened*. Undertakings say *what it was for*. The layer between them is assignment: every session gets a disposition — it belongs to an undertaking, or it has been judged not to be one — and the judging is done by AI proposal plus a human verdict.

This file is written **before** the mechanism, which makes it the odd one out in `docs/contracts/`: the rest were learned from regressions. The reason to write it first is that the failure mode here is not a crash, it is a slow drift into uselessness — an assignment layer that quietly stops assigning is indistinguishable from the AI Activity panel, which already shows everything factual about a session. Every rule below is the answer to a way this feature could become that, and two of them were caught in design review after being coded wrong.

State when written: `ai_activity.assignment.record` is wired and parks answers in `ai-activity/pending-assignments/<sessionId>.json`; `patchSessionUndertakingBlock` writes `undertaking`; `listPendingAssignmentsBlock` and `clearAssignmentBlock` have zero consumers; **0 of 551 chains carry an undertaking**.

- **The point is the judgement. Blank is not a disposition.** (Caught in review 2026-08-02, after the first design had already shipped the wrong framing into a comment.) The first cut of `assignmentSweepBlock` said the invariant was "accounted for, not assigned" — plenty of sessions are noise, so leaving them unassigned is fine, just keep them visible. That is wrong, and it is wrong in the way that kills the feature: a chain that is visible-but-unjudged is exactly what the AI Activity panel already gives you, for free, with no undertaking layer at all. **Every chain gets a disposition, and "not an undertaking" is one of them** — an explicit, recorded verdict, not the absence of a record. The metric to drive to zero is *undisposed chains*, and it is computed by inspection every pass, never stored, because a stored count goes stale the moment anything is stamped.

- **"Not an undertaking" is just another undertaking.** The alternative — a separate `dismissed: true` field on the record — adds a second axis that every reader, filter and count has to learn about, and history says a boolean on a derived record grows a fourth state within a month. Instead it is a per-project bucket undertaking you add chains to, with one flag that keeps it out of calibration stats and out of the DAG. One code path for "where does this chain belong", one correction surface, and un-dismissing is `remove chain from bucket` — the same operation as any other retarget.

- **The sweep proposes over every undisposed session; it does not merely apply parked answers.** The parked answer in `pending-assignments/` is one input, not the job. A pass that only drained that directory would leave the 551 existing chains untouched forever and would only ever cover sessions where the in-session ask happened to fire. The pass enumerates chains (via `listChainProjectsBlock`, reading the *chains* directory and not the project registry, so work under an unadopted key stays visible), filters to the undisposed, and produces a proposal with a confidence for each.

- **Minting is never automatic, at any confidence.** A new undertaking gets a key, and a key is an address — sections file under it, sessions point at it, renaming it later orphans all of them ([DERIVATION.md](DERIVATION.md), first rule). So a proposal that would create an undertaking is *held* for a person, whether the confidence is 0.4 or 0.99, and whether or not the chain has landed yet: the thing needing a human is the minting, not the timing. Attaching to an undertaking that already exists is the opposite — reversible, one wrong pointer, visible in the index, removed with one edit — and may be auto-applied. A key that no longer exists is held for the same reason as a new one: silently recreating it would let a mid-session typo become a permanent address.

- **Never clear the pending ledger.** (`clearAssignmentBlock` already says why and I designed past it anyway: the hook runs twice per session, so clearing after the first run leaves the second run's chain unstamped.) The deeper reason is that **session→undertaking is the durable fact and chain→undertaking is its projection**. Chains are regenerable; after a rebuild, a retained answer re-applies itself and the stamp comes back. Stamping is a union, so a re-run over an already-stamped chain writes nothing. There is no state to garbage-collect here — the ledger is the record.

- **Automation never destroys a human field.** `head` is human-written ([DERIVATION.md](DERIVATION.md), last rule). An auto-applied assignment carrying head text may write it **only when the target head is empty**; otherwise it appends a dated line via `addUndertakingNoteOrch`. `updateUndertakingHeadOrch` overwrites, so it is a human-only path. Same for the correction surface: `key` is write-once, rename touches title and head only.

- **The correction surface is two operations: rename, and add/remove sessions.** (User's call, 2026-08-02: "the actions are a bit effy and over engineered.") The first design had detach, merge, split and reopen as first-class actions; all four are compositions of the two primitives — merge is remove-then-add plus a rename, split is a mint plus removes, detach is a remove, reopen is a rename. Four operations to implement, test, undo and explain, where two do the job. If a proposed fifth action is expressible as a sequence of these two, it is a UI affordance, not a new operation.

- **Log every verdict from day one, append-only.** `{sessionId, proposed, confidence, verdict: accept|reject|modify, correctedTo, at}`. It is three things at once and all three are needed later: the training signal that decides when a confidence band is trustworthy enough to auto-apply, the correction history that makes a wrong auto-apply diagnosable, and the audit trail for a layer where a machine writes into judgment fields. Retrofitting it means the first months of calibration data — the months where the model is worst and the corrections are most informative — are gone.

- **Auto-applied is never invisible.** Escalation to accept-as-default happens per confidence band, driven by the verdict log, and everything auto-applied lands in a recent-auto list with one-key undo. A silent write into a judgment field is how the layer loses the user's trust in a single bad week.

- **Granularity is calibrated against the head, not against the session.** If the head reads like a commit message, the undertaking is too granular; if you cannot write one honest line for it, it is too high-level. Calibration from this vault's own history: F9 ran ≈16 undertakings/month, old thinkingspace.ai ≈10/month → **~2–4 per active week**, so 222 `Thinking-Space` chains should collapse to roughly **40–70 undertakings**, not 200 and not 8. **Err granular**: merging two undertakings is lossless, splitting one is a reconstruction from memory.

- **The unit is the session, not the chain.** (Changed 2026-08-14.) A chain groups by *time* and can therefore hold two unrelated topics; an undertaking is a *topic*. Binding at the chain level is how a Broadcom undertaking came to list four Important-Personalities notes as its pages — a 20-second gap made them one chain and the disposition had no way to say "this half, not that half". The session is the finest thing the transcript distinguishes, so the misattribution is now unrepresentable rather than merely unlikely. The cost is roughly 1.5x the rows (chains average 1.49 sessions), absorbed by *displaying* rows grouped into their sitting while *deciding* per session: grouping is presentation, disposition is data. A session id is also stratum-1, which matters more here than anywhere else — this log is append-only and replayed years later, so its key must name something no re-grouping can rename. See [DERIVATION.md](DERIVATION.md).

- **The queue is the product.** Not the assignment, not the index — the queue. The user's constraint is explicit: "the moment I am involved things slow down." So it groups by *proposal* rather than by chain (one keystroke disposes of six chains that belong together), sorts by confidence descending, is keyboard-first with three keys — accept, retarget, bucket — and skipping is free with no penalty and no re-prompt loop. Anything that makes the queue slower to clear is a regression in the feature itself, not a UI nit.

- **The ritual anchors to shipping, not to session lifecycle.** A session end is a context-window event; it has no relationship to whether a piece of work finished. A ship is a work event. Capture is already lifecycle-independent — `nativeAiSessionsBlock` reads `~/.claude/projects/<encoded-cwd>/<sessionId>.jsonl` directly, so abandoned, limit-hit and never-compacted sessions all still become chains — so nothing is lost by declining to hang the prompt off session end.
