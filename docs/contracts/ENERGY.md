# Energy Contract (Enforced, learned 2026-07-25; Mac scope added 2026-08-11)

Battery is a first-class constraint on iPad — the app is a reading tool, so long sessions on a device that is not plugged in are the normal case, not the edge case.

**Mac bar (added 2026-08-11):** the app must stay smooth on a base MacBook Air in Low Power Mode on efficiency cores. Measurable form:
- **Idle** (app open, no interaction, 60s): < 1% total CPU across all processes; no periodic wakeup that isn't tied to visible on-screen state.
- **Reading / panning on E-cores only:** sustained 60fps, < 15% CPU.
- **Resident:** < 600 MB total, GPU process < 250 MB.

**This contract covers the main process too, not just the renderer.** It was written renderer-first and that gap hid the single largest energy cost in the app: `vaultWatcherBlock` set `usePolling: true` with `interval: 2000, depth: 99` for iCloud vaults, so a 20k-file vault was ~10k `stat` syscalls/second plus a full JS diff, forever. Measured 2026-08-11 on a live instance: **main process 67–84% CPU while completely idle**, `/usr/bin/sample` showing libuv workers in `scandir`/`stat` and the main thread in `node::fs::AfterStat`.

  **FIXED 2026-08-11 (`c3471e6`) — main process now measures flat 0.0% at idle, across a restart and a full startup sync.** Two causes, and the second is the one worth remembering:
  1. *The premise was never tested.* Polling existed on the belief that iCloud does not emit FSEvents for external writes. Tested against the real 20,842-file vault: an unrelated Node process creating, appending to, and deleting a file produced clean `add`/`change`/`unlink` events with polling **off**, at 0.1% of one core. A comment justifying 80% CPU was simply wrong, and nobody had checked it.
  2. *A self-sustaining loop.* `.thinking-space/` was not ignored, and `home-snapshot.json` is regenerated after every sync — so sync wrote the snapshot, the watcher reported it, the renderer synced, repeat. Self-write suppression should have broken this, but its window is 3s (`selfWriteTrackerBlock.WINDOW_MS`) while polled events arrived at 2.3s+, so it missed intermittently. The file was being rewritten every ~2s, 37KB, into an iCloud-synced folder, with the app idle.

  **Do not reintroduce polling here.** The case FSEvents may still miss is a change syncing *down* from another device; that is covered by the focus/visibilitychange reconciliation in `vaultLiveRefreshOrch` — a full vault walk costs ~0.13s warm, affordable on focus and ruinous at 2s intervals.

  **Method note, since it cost most of a day:** always confirm which PID is which. An early reading reported "renderer 36.5%, GPU 21%" with the labels swapped; the truth was GPU 35.7% / renderer 21.2%, which points at compositing rather than JS and changes the entire diagnosis. `ps ax -o pid,command | grep -i "Thinking Space"` before believing any per-process number.

- **An animating element is only expensive if something is actually driving frames — measure before believing a CSS-cost argument.** This bullet used to assert that the four `[data-canvas-edge]` aurora layers (blurred, `mix-blend-mode`, animating `background-position` — a paint property, non-composited in every engine — forever, at `opacity: 0`) were a significant idle cost. **Measured 2026-08-12: they are not.** With the moon scene panned off screen the GPU process sat at 1.8% while all four aurora layers were mounted and "animating". Chromium skips them entirely at `opacity: 0`. The reasoning was sound and the conclusion was wrong; the aurora stays.

  What *is* true is the inverse, and it is the more useful rule: **one cheap animating element can be expensive because it forces a compositor frame, and the frame's cost is whatever else is on screen.** The moon scene is the only thing driving continuous frames on the home canvas, and removing it from view took GPU from 35.7% to 1.8%.

- **Give a continuously-animating subtree its own compositing layer.** `MoonSceneBlock` runs ~18 infinite animations with no `will-change`, so they repainted into the shared 4500×4500 canvas world layer — a 520×240 pixel-art scene dirtying a 20-megapixel surface 60 times a second, with each sprite a 1px div carrying up to 100 `box-shadow` entries (`PixelSprite`/`spriteShadow`) to re-rasterize. One line of `will-change: transform` on the scene root confines the invalidation and took **GPU 35.7% → 24.9%** (`a898c92`), with no visual change. Note it did *not* fix it: ~23 points remain, and the leading suspect is layer squashing forcing those box-shadow sprites to re-raster as a group. Promoting the animated *children* individually is not the answer — Chromium already auto-composites running transform/opacity animations; the unpromoted root was the part it does not handle.
- **Measure canvas changes with the frame recorder, not with your eyes or your model of CSS.** Three canvas "optimizations" shipped in a single day on reasoning alone; two regressed and were caught only by a human noticing dropped frames. `frameTimingBlock` + the Frame Timing section in the debug panel's Performance tab record rAF deltas while you drive the canvas (also `window.__thinkspc_frames.start('label')`). It only runs while recording, so it does not violate the contract it defends. **Record the same interaction at both zoom extremes** — that is where every regression here has hidden.

- **A world-sized masked layer is expensive, but "always viewport-sized" is not the fix — measure both zoom extremes.** `CanvasBloomBlock` is `worldWidth × worldHeight` (4500 × 4500 = 20MP, 81MP at 2× retina) carrying a tiled gradient plus a gradient mask, repositioned via `left`/`top`, so every pan frame invalidates layout and re-masks an area that is transparent by construction outside the ~340px glow. **Attempted and reverted 2026-08-11** (`8b96d75`, reverted in `be043d5`; work preserved on `perf/canvas-paint`): making it viewport-sized with `background-position` anchoring and a `clip-path` reproducing the old bounds. GPU process RSS correlated down ~1.0 GB → ~412 MB, but it **dropped frames when fully zoomed out** — at min scale the world-sized element is only ~1125px across, so a fixed viewport-sized element with a per-frame `clip-path` is *larger and more expensive* than what it replaced. The element's cost scales with zoom; any replacement must be measured at both extremes, not just zoomed in. A `min(world, viewport)` sizing is the obvious next attempt.

  **RESOLVED 2026-08-12 (`cdd48ee`).** `CanvasBloomBlock` is deleted; `CanvasGridBlock` inverts the shape. The clip container keeps the board's geometry but paints nothing, and the only painted element is a fixed 880×880 pool following the pointer by `transform` alone — rasterized once, never resized, and **smaller than the old element at every zoom**, which is the property the two failed attempts lacked. The pool's translate snaps to whole multiples of `dotSpacing`, so the lattice stays anchored and `background-position` (a paint property) is never touched; the reveal centre is off by ≤ half a spacing, invisible under a radial falloff. Pointer movement writes through a ref and never re-renders React.
- **No unconditional periodic timers.** A repeating `setInterval` is the single most reliable way to keep a CPU out of its deep idle states, so every interval must be gated on something. `startStallDetector` (`mainThreadStallBlock`) ran at 100ms forever from App mount and merely *reset* its heartbeat on `visibilitychange`; it now **stops** the interval while hidden and restarts on return (fixed 2026-07-25). When adding a timer: gate it on `document.visibilityState === 'visible'` AND on the feature actually being on screen, and prefer event/observer-driven updates over polling.

  **Use `useVisibleIntervalBlock` (`hooks/shared/`) — do not hand-roll a `setInterval` in a component.** It stops on `visibilitychange` and re-fires the callback on resume, so nothing is stale on the frame the user returns to; pass `null` as the period to disable. All ten renderer pollers were migrated to it 2026-08-11 (250ms sync clock, 500ms banner clock, 700ms `UrlDocumentBlock` webview probe, 1s `DebugPanelBlock` ×2, 3s `AiSettingsOrch`, 15s `ScheduleListBlock`, 30s `CodexUsageProbeBlock` + moon messages, 60s `useTimeOfDayBlock` + `useSessionTelemetryBlock`).

  **"Gated on mount" is not gated.** Every one of those ten was already conditional — inside a page that only renders on that route, or behind an `enabled` flag — and every one still ran forever in a backgrounded window. Mount-scoping bounds *where* a timer runs, not *whether* it runs while nobody is looking. Grepping for `visibilityState` to find offenders will also mislead you in the other direction: several sites early-return on an empty work queue and look ungated to a grep while being perfectly well behaved. Read the effect.

  The two webview probes gate in place rather than through the hook, because their callbacks are defined inside effects that also wire `did-finish-load` listeners. `useSessionTelemetryBlock` keeps a `focus` listener *alongside* the hook: **in Electron a blurred-but-visible window never fires `visibilitychange`**, so `focus` is the only event that catches "user came back to the window."
- **Reading holds the display awake; nothing else does.** WKWebView does NOT expose the Screen Wake Lock web API, so iOS goes through native `UIApplication.isIdleTimerDisabled` (`IdleTimerPlugin.swift`, registered in `AppDelegate.capacitorDidLoad`). Renderer surface is `screenWakeLockBlock.ts` (unit): **counter-based leases** mirroring `nativeChromeImmersionBlock` so overlapping readers compose, native on iOS / `navigator.wakeLock` elsewhere / silent no-op if neither (never surface an error for a comfort feature). Consumed via `useScreenWakeLockBlock(active)` in `MarkdownDocumentBlock`, scoped to `active && (!isEditing || isExcalidrawDoc) && !loading && !error` — editing already generates taps that satisfy the idle timer, **except on an Excalidraw canvas** (extended 2026-08-25), which is a reading surface in both modes: you hold a diagram or a page of handwritten notes on screen and think, and a hovering Apple Pencil is not a touch. Widening the condition was the whole change — the canvas already renders inside `MarkdownDocumentBlock`, so it inherits the same active/visible scoping and the same Settings toggle; do not add a second lease site for it. Setting: Settings ▸ Theme, `getReadingKeepScreenAwake()`, **default ON** (safe because iOS drops the flag itself the moment the app backgrounds, so a stuck lease cannot drain the battery in the background). The **web** wake lock is dropped on hide and NOT auto-restored by the browser, so `screenWakeLockBlock` re-acquires on `visibilitychange` — without that, one app-switch silently kills the lock for the rest of the session.
- **Adding a new `.swift` file requires 4 manual `project.pbxproj` edits** (PBXBuildFile, PBXFileReference, group children, Sources build phase). The Xcode project is NOT a `PBXFileSystemSynchronizedRootGroup`, so a new file silently does not compile if you skip this. `IdleTimerPlugin.swift` mirrors `VaultWalkPlugin.swift`'s entries.
- **Wake-lock and any native plugin change need a real `cap sync` + xcodebuild** — `./scripts/checkpoint-ship-ios.sh`. A web-only bundle push will not pick it up.
- Suspected-but-unmeasured energy costs (do NOT "optimize" before instrumenting): the ~853 MB idle footprint (memory pressure costs energy directly), and 11 `backdrop-filter` rules (each a live GPU blur pass that recomposites every scroll frame at 2× retina — the steady-state cost while reading, i.e. exactly when the wake lock now holds the screen on). Measure with `xcrun xctrace record --template 'Energy Log'` before changing either.

- **Automatic multi-minute model runs require wall power.** A session digest is a local-model run that routinely takes 400–600s (visible in the debug console's AI runs tab), and opening the AI Activity panel over a wide range asks for one per session — so a single panel mount can turn into hours of GPU on a laptop that is unplugged. The gate lives in `powerStateBlock` (renderer integration; main-process probe in `electron/src/lego_blocks/powerStateBlock.ts`) and is applied at three call sites, all of which take the same `{ refresh }` option: `ensureSessionDigestOrch`, the chain stitch in `ensureChainDigestOrch`, and `ensureRangeSummaryOrch`.

  Three rules make it safe:
  1. **The gate only sees automatic runs.** `refresh: true` — the regenerate button, and the bulk regenerate in `AiActivityPanelBlock` — never reaches it. A person asking is not a background loop deciding, and the override is the escape hatch that lets the gate be strict.
  2. **Blocked is not failed.** Any stored digest still surfaces; the refusal returns the un-persisted rule-based fallback plus a `blocked` reason, so plugging in and reopening generates the real thing. The UI must say why (`heavyWorkBlockedLabelBlock`), or a rule-based title reads as the model's bad answer rather than as a pause.
  3. **Unreadable power state is permissive.** Web and iOS have no power API; blocking there would silently kill digests on surfaces with no battery problem. `known: false` disables only the Low Power Mode half — Electron's `powerMonitor.onBatteryPower` is native and still counts.

  **The pmset key is `powermode`, not `lowpowermode`.** On Apple Silicon `pmset -g` prints ` powermode 0|1|2` (automatic / low / high) for the currently-active source; `lowpowermode` is the Intel-era spelling and appears valueless in `pmset -g everything`. The first version of this block looked only for `lowpowermode` and would have parsed nothing and never fired — a gate that fails open fails silently, which is why `parseLowPowerModeBlock` is unit-tested against verbatim `pmset -g` output. Only mode 1 blocks; High Power (2) is the opposite of a reason to hold back. The probe is cached (30s in main, 15s in the renderer) and invalidated on `on-ac`/`on-battery`/`resume` — **no timer keeps it warm**, per the rule above.
