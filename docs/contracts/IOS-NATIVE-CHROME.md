# iOS Native Chrome Decisions (locked 2026-07-19)

- **Top status-bar veil is STATIC glass, never Liquid Glass and never scroll-linked.** `TopChromeView` uses one soft masked progressive blur (solid to 30% of the strip, feathered to clear); scroll must not deepen/animate it — the earlier scroll-linked "breathing" read as a glitch. Liquid Glass (`glassEffect`) is for discrete floating controls (bottom chrome capsules), not edge scrims: glass needs a shape boundary and can't feather to nothing.
- **Bottom chrome collapses Safari-style** (`BottomChromeView`): at rest = hamburger/back + tabs pill + optional side-panel toggle + chevron menu; on scroll everything except the pill scale-fades away and the pill shrinks into one small CENTERED chip (badge + active tab name). Tap chip / scroll-up restores. No half-pill fragments.
- **Native side-panel toggle button** (mirrors Electron's `SidebarChromeButtonBlock`, emits `topChromeSidebarToggleTap`) shows only where the native chrome is the sole way to reach the panel: Chat, Web, Settings. Hidden (`enabled: false` in App.tsx `nativeSidebarControl`) on Thinking Space explorer, Webull/F9, and Thinking Organizer — their iPhone list/detail layouts own the panel. **New Note has no side panel at all** (removed 2026-07-31): it is one full-bleed iA-Writer-style writing surface, and its destination/settings config opens as a bottom sheet from a title-bar button, never as a panel. The chevron "More Options" menu has NO drawer entry.
- **Tab switcher is a Safari-style card grid** (`NativeTabSwitcherSheetView`): 2-col grid, live WKWebView snapshots (`captureActiveTabSnapshot` in RootShellViewController, 420pt wide, captured right before the sheet presents, pruned to live tab ids, in-memory only in `TopChromeState.tabSnapshots`), monogram glass placeholder for unvisited tabs, accent ring on active, dashed New Tab card.
- **iPhone explorer header is one icon row**: filter input collapses to a toolbar Search button via `VaultExplorerBlock collapseSearchToButton` (prop doubles as the phone-surface flag), RSS toggle rides `toolbarActionsSlot` on all surfaces (full-width RSS row removed), File-info `(i)` button is desktop-only.
- **iPad top bar is ONE row with a Files-app centered tab pill** (replaced the two-row Safari segmented bar 2026-07-19 — a lone tab stretched full-width read as a broken title bar): hamburger/back left, centered Liquid Glass pill (`padFilesTabPill` in TopChromeView) holding sidebar toggle (portrait) + content-hugging tab segments (active = soft highlight + ✕) + hairline divider + `+`/grid folded into the trailing edge, search/refresh/⋯ right. Sync lives in the ⋯ overflow menu (like Electron), not the bar; the ⋯ Menu label needs `.tint(.primary)` or SwiftUI paints it accent-blue. Bar height = 48pt: `nativeChromePadBarHeight` ↔ two `48px` clearance rules in index.css ↔ PhoneShellView veil depth — keep all three in sync. In **landscape** the sidebar toggle separates out of the pill into its own glass button at far left (Electron position); the pill drops it. iPad `+` = plain new tab (lands on Home); iPhone dock `+` = create note (`openNativeCreateSurface` splits by idiom).
- **iPad tab switcher is an anchored POPOVER off the pill's grid button** (compact `NativeTabSwitcherSheetView compact:true` — no title row, card-count-sized frame); the phone keeps the full sheet with Tabs/Done header. Card grid details (snapshots, monogram placeholders, dashed New Tab) shared between both.
- **Drawer compaction (iPad)**: while the left drawer is open, the top chrome container gets a leading inset equal to the drawer slide offset (`bottomChromeLeadingConstraint` in `applyDrawerVisualState`, same spring) so the bar squeezes into the visible content area instead of being buried; `chromeState.drawerProgress` is set there too (the iPad path never wrote it).
- **Immersive focus mode hides the native chrome**: fullscreen web overlays (Excalidraw focus) hold a counter-based lease via `nativeChromeImmersionBlock` + `useNativeChromeImmersionBlock(active)`; App.tsx passes `visible: !immersed` through the top-chrome bridge (hides bar + veil on both idioms, mirrors Electron focus-owns-the-window). CRITICAL: the veil must set `.allowsHitTesting(false)` **unconditionally** (tightened 2026-08-01 from `.allowsHitTesting(chromeState.isVisible)`). `TopChromeView` is a scrim — a masked material rectangle carrying no controls on either idiom — so every touch it accepts is stolen from the web content beneath. The old form only fixed the hidden case (immersive focus mode, where the invisible strip blocked the focus header's Exit button); the visible case is the same bug, because the veil runs `safeTop + 24` and its feathered tail covers the top ~24pt of whatever the page places under the status bar. New Note's title-bar controls sit exactly there and lost half of each 44pt tap target to it. **If you ever put an interactive control inside `TopChromeView`, this line has to change — and the control needs its own hit-testing island rather than re-enabling it for the whole scrim.**
- **Native owns the left-edge swipe**: the web's edge-swipe drawer handler stands down on ALL native-chrome surfaces (`useNativeTopChrome` guard in App.tsx), and the Swift `UIScreenEdgePanGestureRecognizer` needs a `shouldRecognizeSimultaneouslyWith → true` delegate or WKWebView's internal scroll recognizers win the race and it never fires over web content.
- **Overscroll = content bounces, backdrop stays pinned** (native model): edge-bleed page backdrops are `position: fixed` to the viewport on capacitor phone AND tablet (the tablet rule must live at top level — iPad Pro portrait is 1024px, outside the 1023px media query), so the rubber band reveals more backdrop, never the flat shell background. Do NOT kill vertical bounce. Graph canvas (`VaultGraphCanvasBlock`) sets `touch-action: none` on its mount — the shell's `touch-action: pan-y` otherwise lets the browser eat all canvas touches.
- **The keyboard's accessory bar is ours, and it is one blue ✓** (`LTMKeyboardAccessoryBar` + `installKeyboardAccessoryBar` in AppDelegate.swift, 2026-08-01). WKWebView otherwise hands every focused field UIKit's form bar — ‹prev› ‹next› ✓ for tabbing between form fields, three dead controls in a one-field editor and visibly unlike a native app's keyboard. There is no API: the getter lives on the private WKContentView, so the override goes on in the ObjC runtime. Use `class_addMethod` on that class (falling back to `method_setImplementation` on **its own** method — never UIResponder's, which every responder inherits). Do NOT `object_setClass` the live instance: that was the first version and it cost the selection grabbers, because WebKit's text-interaction assistant is keyed off that view. The bar sizes from its frame (`sizeToFit` does not apply to accessory views) and must clear the round prominent `.done` button — at the toolbar's natural 44pt the circle overhangs into the keyboard. **Whatever replaces it must still dismiss the keyboard**: with the native bar gone there is no other affordance, and shipping without one stranded the editor for a build.
- **A full-bleed page owns the bottom edge too.** App.tsx pads the main stage by the keyboard inset when the keyboard opens, which shrinks the card-white page and shows a band of shell grey above the keyboard. `.ltm-page-flush-top` drops that padding at both edges (the bottom rule needs `!important` — the padding is an inline style); the editor clears its own content with `--ltm-focus-keyboard-inset`. Note the inset reads ~44pt taller than the keyboard because WKWebView still budgets for the accessory bar.
- **A modal sheet takes the immersion lease, it does not dodge the dock.** New Note's settings sheet calls `useNativeChromeImmersionBlock` while open, so the bottom dock hides instead of floating over the sheet's last rows; the sheet then pads to the safe area only. Reserving the dock's height was the earlier fix and left dead space once the dock could hide.
- **Centered title bars need fixed-width flanks.** The New Note bar is `grid-cols-[1fr_auto_1fr]`, and the flanks only share space evenly while they are the same width — so a right cluster whose contents come and go (save badge, manual-save button) slides the centered filename on every change. Pin the cluster's column width. It is also NOT `min-w-0`: an overflowing `justify-end` flex row spills *leftward*, which is how the icons ended up painted over the filename in the first place.
- **The drawer's rail is pinned edge-to-edge, not to the safe-area guide.** `railHostingVC.view` spans `leftDrawerContainerView`'s full top-to-bottom (fixed 2026-08-01). RailView's frosted material is `.ignoresSafeArea()`, which only works if the host has room above safe-top to bleed into — pinned to `safeAreaLayoutGuide.topAnchor` the material began exactly at safe-top and the container's flat background showed above it as a horizontal seam under the status bar. SwiftUI still propagates the insets, so the MENU header stays put. Same reason `DrawerHeaderView` carries no background of its own: the drawer is one continuous material surface, and anything opaque laid on it reads as a seam.
- **A desktop sidebar reused as a phone page needs phone metrics, not just `flex-1`.** Webull/F9, Thinking Organizer and Settings all render their 220–258px desktop nav as the iPhone list page. Left alone it keeps desktop rows (26–32px tall, well under the 44pt floor). Gate on the page's `phoneListMode` and render `PhoneListBlock`'s inset-grouped primitives (`PhoneListSectionHeaderBlock` / `PhoneListGroupBlock` / `PhoneListRowBlock`) rather than restyling the desktop button — 44pt rows alone still read as a web nav, because what makes an iOS list an iOS list is the filled card with text-inset hairlines, full-contrast labels, a chevron on anything that pushes, and an `active:` press state (`hover:` never fires on touch, so a tap had no feedback until the next screen appeared). Inputs go `h-11 text-base` (under 16px Safari zooms the page on focus). Drop the active-row highlight — it is feedback for a detail pane that is already on screen, and in list/detail the row is gone before it would show. Settings joined the pattern 2026-08-01; side by side its detail pane got ~40% of the screen and wrapped prose one word per line. When a page switches to list/detail on phone it must also stop advertising its sidebar toggle (`dispatchSettingsSidebarChromeStateBlock({ enabled: !isIPhoneIosSurface })`) — the button would collapse a pane that no longer exists.
- **The large title bar is web, not UIKit, and it is also the status-bar backdrop.** `PhoneLargeTitleBlock` renders a sticky compact bar plus a big title that scrolls under it, as the first child of the page's scroller. It returns a **fragment, not a wrapper**: `position: sticky` is confined to its parent's box, so wrapping the bar and the title together makes the bar scroll away the instant the title does — its parent has to BE the scroller. Consequently these pages carry no top/side padding on their scroller (the bar spans edge to edge, rows inset themselves via `PhoneListGroupBlock`) and no safe-area inset of their own (the shell already pads `.ltm-app-main` by `--ltm-safe-top`; padding here too stacks two status bars of dead space). The compact bar needs `isolate` + explicit `z-0`/`z-10`: `backdrop-filter` promotes the frosted layer to its own compositing layer and WebKit then paints it *over* later siblings with `z-index: auto`, which hid the compact title moments after it faded in. A page whose toolbar must stay reachable parks it as a second sticky row at `top-11` with an opaque background (Explorer, via `VaultExplorerBlock`'s `phoneLargeTitle` — which also folds that component's two boxes into one scroller). It is deliberately not a `UINavigationBar`: these pages scroll in the web view, so a native bar would need the web scroll offset bridged to Swift every frame — a JS→native hop in a 60fps path for something that is pure presentation. Collapse is measured off the big title's rect passing the bar's, not a fixed `scrollTop`, so the handoff reads as one motion. Its second job is structural: before it existed these pages reserved nothing above their content and rows scrolled under the status bar with no backdrop.
- **Nothing reserves room for the bottom dock.** It floats over the web view, 64pt above the home indicator (`resolvedBottomChromeHeight`), and `bottomOffset` in `uiNavigationBlock` is zero under native chrome because the web nav is hidden. A scrollable phone page must pad its own scroller — `pb-[calc(var(--ltm-safe-bottom,0px)+5.5rem)]` — or its last row can never be scrolled clear. Applied per page today (F9, Organizer, Settings); if a fourth needs it, make it a shell rule instead.
- **Electron corner treatments don't cross to iPhone**: `.ltm-thinking-space-document-stage` keeps its rounded-right/flat-left corners only where it sits beside the explorer; iPhone full-screen detail zeroes radius + margin.

## Vault-Sync Indicator (locked 2026-07-19)

The refresh pill IS the sync indicator on every platform — sync never gets its own surface. Design iterated hard: banner → top-edge hairline (rejected: "very bad UI") → this. Do not resurrect either.
- `backgroundActivityBlock` activities carry `channel: 'ambient' | 'alert'`. Vault syncs (`vaultSyncOrch` full + incremental) publish `ambient`; `BackgroundActivityBannerBlock` renders only alerts (capability calls, main-thread stalls) — the banner is the escalation surface, never routine sync.
- `useAmbientSyncActivityBlock` (hooks) is the single source of truth: `running` turns true only after a sync has been in flight **500ms** (sub-threshold watcher churn shows nothing anywhere); exposes aggregate progress fraction + completed/total file counts.
- Desktop: `SyncRefreshButtonBlock` (units) — icon-only pill (no "Refresh" word), click still = cheap UI refresh (`handleGlobalRefresh` does NOT sync; that separation is deliberate — sync fires from startup/watcher/manual rebuild). While syncing: icon spins, a small accent progress circle hugs the **icon** (not the capsule — survives the capsule widening), determinate syncs widen the pill with a tabular `completed/total` count, completion = circle closes + fades (min one ~650ms pulse).
- iOS: same threshold/state rides the bridge as `syncActive`/`syncCompleted`/`syncTotal` (TopChromeStateBlock → TopChromePlugin → TopChromeState.syncProgress). `SyncSpinIconView` (TopChromeView.swift) draws the ringed spinning arrow; iPad = top-bar refresh button widens with count, iPhone = bottom pill shows ring+count in the full bar, ring only in the minimized chip.

## Cross-Device Settings Roaming (locked 2026-07-19)

- **The roaming mechanism is `.thinking-space/preferences/ui.json`** via `vaultUiPreferencesOrch` (typed, normalized, read-merge-write). Do NOT invent parallel settings files — extend `VaultUiPreferencesBlock` instead. AI-activity display prefs roam through its `aiActivityPrefs` group (null = unset → device default): startup pull applies vault values through the public storageKeyBlock setters (their events fire, UI updates live), local changes push back debounced via the `registerStorageWriteListenerBlock` hook in storageKeyBlock (`initAiActivityPrefsRoamingOrch`, wired in App.tsx once the vault is ready). Device-bound settings NEVER roam: intelligence provider endpoints, AI-activity range-summary provider (Claude CLI exists only on Electron), vault paths, per-profile nav rail layout.
- **User profile (name/symbol/memories) roams via `.thinking-space/profile.json`** (its own file, predates ui.json roaming). Two iCloud hazards are guarded: `CapacitorVaultFS.exists` treats `.NAME.icloud` placeholders as existing (undownloaded ≠ absent), and `readUserProfileOrch` never seed-writes a pure-default profile over the vault (`isDefaultUserProfileBlock` guard) — a fresh device once clobbered the real profile with "You" through that path.
